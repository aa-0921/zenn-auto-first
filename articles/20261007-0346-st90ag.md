同じコードを何度も手で打っていたり、エラーで詰まったりした経験はありませんか？ 私は個人開発で何度も同じコマンドを繰り返し実行し、作業が手間に感じることがありました。ここでは、そんな悩みを解決してくれた 10 個の GitHub Actions ワークフローを紹介します。それぞれの「困っていたこと」「使い方」「変化した点」を具体的に紹介しますので、ぜひ参考にしてみてください。

## PR が作成されたら lint とテストを自動実行

昔、ブランチをプッシュするたびにターミナルで `npm run lint && npm test` を実行し、結果を確認していました。エラーが見つかると作業が中断され、CI 環境で同じチェックをしたいと思っていました。

```yaml
- name: Lint and Test
  run: |
    npm run lint
    npm test
```

これを使うと、PR 作成時に lint とテストが自動的に走り、早期に問題を検出できるようになりました。手動での確認が不要になり、作業がスムーズになりました。

## タグがプッシュされるたびに Docker イメージをビルド＆プッシュ

昔、タグ付きリリース時に手動で `docker build -t myapp:$GITHUB_SHA .` と `docker push` を実行していました。CI 上で自動化したいと思っていました。

```yaml
- name: Build and Push Docker Image
  run: |
    docker build -t myapp:$GITHUB_SHA .
    docker login -u $DOCKER_USER -p $DOCKER_PASS
    docker push myapp:$GITHUB_SHA
```

これで、タグプッシュ時にイメージのビルドとレジストリへのプッシュが自動的に行われ、手動での手間が省け、リリースプロセスが確実になりました。

## 毎週月曜の朝にバックログを自動集計

以前は毎週月曜に手動で `gh issue list --label bug --state open` を実行し、集計レポートを作成していました。自動化したかった。

```yaml
- name: Weekly Bug Count
  run: |
    bugs=$(gh issue list --label bug --state open --json number --jq '. | length')
    echo "Open Bugs: $bugs" >> $GITHUB_ENV
```

これで毎週月曜に環境変数にバグ数が格納され、スプレッドシートへの手動入力が不要になりました。

## 依存関係更新時に PR を自動作成

手動で `npm outdated` と `npm update` を実行し、PR を手動で作成していました。自動化を希望。

```yaml
- name: Create Dependabot-like PR
  run: |
    npm update
    git config --local user.email "action@github.com"
    git config --local user.name "GitHub Action"
    git add package.json package-lock.json
    git commit -m "chore: update dependencies"
    git push origin HEAD:dependabot-updates
    gh pr create --title "Dependabot Updates" --body "Updated dependencies"
```

これで依存関係更新が自動で PR になり、手動の PR 作成作業が省けました。

## プルリクエストのタイトルにキーワードが含まれているかチェック

以前は手動でタイトルに「fix:」や「feat:」が含まれているか確認していました。自動化が必要。

```yaml
- name: Validate PR Title
  run: |
    title=$(gh pr view $PR_NUMBER --json title --jq '.title')
    if [[ ! $title =~ ^(fix|feat|chore|docs|style|refactor|test|ci|revert)(\(.+\))?: .+ ]]; then
      echo "::error::PR タイトルが規約に沿っていません"
      exit 1
    fi
```

これで PR 作成時にタイトル形式のチェックが自動で行われ、不備のある PR が減りました。

## タグ付きリリース時に Slack に通知

手動でリリースノートを作成し、Slack に投稿していました。自動化が必要。

```yaml
- name: Notify Release on Slack
  uses: 8398a7/action-slack@v3
  with:
    status: success
    channel: '#releases'
    text: "New release ${{ github.ref_name }} is out!"
```

これでリリース時に Slack チャンネルに自動通知が届き、手動での投稿が不要になりました。

## コード内の未使用変数を探して警告

手動で `eslint` を実行し、未使用変数を確認していました。自動化が必要。

```yaml
- name: Check Unused Variables
  run: |
    npm install -g eslint
    eslint . --config .eslintrc.json --no-eslintrc --output-file eslint-report.json
```

これでコミット時に未使用変数の警告が自動表示され、コードの品質が向上しました。

## 特定ブランチへの push 時にセキュリティスキャン実行

手動で `npm audit` を実行していました。自動化が必要。

```yaml
- name: Run Security Audit
  run: |
    npm audit --audit-level moderate
```

これで push 時に脆弱性チェックが自動実行され、問題のある依存関係を早期に発見できるようになりました。

## 毎日 0 時にスターターテンプレートの検証

手動でテンプレートリポジトリをチェックしていました。自動化が必要。

```yaml
- name: Validate Templates Daily
  run: |
    find . -name '*.yml' -o -name '*.yaml' | xargs yamllint -c .yamllint.yml
```

これで毎日テンプレートの YAML 構文が自動チェックされ、誤った設定を未然に防げます。

## フォークしたリポジトリのスターを自動カウント

手動で GraphQL をクエリしてスター数を取得していました。自動化が必要。

```yaml
- name: Count Forks Stars
  run: |
    stars=$(gh api repos/$OWNER/$REPO/stargazers --jq 'length')
    echo "Stars: $stars" >> $GITHUB_ENV
```

これで環境変数にスター数が格納され、手動での API クエリが不要になりました。

## まとめ

これらの 10 個の Actions は、個人開発のワークフローを劇的に改善してくれました。まずは 1 つ試してみてほしい。小さな自動化でも、積み重ねれば大きな効率向上につながる。ぜひ、自身の開発スタイルに合ったものを追加してみよう。
