## ルーティングエラーの正体と対処法

### 「No route matches」が出たとき

もっとも多いのは次のエラーです。

```
ActionController::RoutingError (No route matches [GET] "/articles/published"):
```

パスが存在しないため、Rails がどのコントローラ・アクションに渡すべきか判断できていない状態です。ここで初心者がやりがちなのは、コントローラに `published` アクションを追加してしまうことです。しかしルーティングに定義がなければ、アクションを書いても永遠に呼ばれません。

まず `config/routes.rb` を確認し、`resources :articles` だけになっていないかを見ます。カスタムアクションを追加するなら、次のように `collection` か `member` を明示的に書く必要があります。

```ruby
Rails.application.routes.draw do
  resources :articles do
    collection do
      get :published # /articles/published
    end
    member do
      patch :publish # /articles/:id/publish
    end
  end
end
```

`collection` と `member` の違いは「ID を必要とするか」です。一覧に対して行う操作（検索、公開中リストの取得など）は `collection`、特定の1件に対して行う操作（公開する、削除する）は `member` を使います。この区別が曖昧なまま `resources` だけ書くと、後から「URL が引けない」という形で必ず困ります。

### ヘルパーメソッドが nil になる

ルーティングがらみのもう一つの定番は、ビューでこんなエラーが出るケースです。

```
ActionView::Template::Error (undefined method `article_path' for #<ActionView::Base>):
```

`article_path` というヘルパーが定義されていない、つまり `resources :articles` の `articles` が複数形・単数形のどちらかを取り違えている、あるいはそもそもルーティングが無い、というサインです。`rails routes` の出力の Prefix 列がそのままヘルパー名になるので、推測せずコマンドで確認するのが確実です。

なお、モデルとルーティングの命名がずれていると `form_with` でも詰まります。

```erb
<!-- Article モデルだがルーティングは resources :posts になっている場合 -->
<%= form_with model: @article do |f| %>
```

このとき Rails は `articles_path` を推測して失敗します。明示的に `url:` を渡すか、ルーティングとモデルの命名を揃えてください。

### Unpermitted parameters はセキュリティ機構

```
Unpermitted parameters: :admin. Context: { controller: ArticlesController, action: update }
```

これはエラーではなく「許可していないパラメータが送られてきたので捨てました」という通知です。許可するには Strong Parameters を更新します。

```ruby
def article_params
  params.require(:article).permit(:title, :body, :published)
end
```

ネストした構造や配列は `permit` の書き方が変わるため、次のように覚えておくと応用が効きます。

```ruby
params.require(:article).permit(:title, tags: [], author_attributes: [:name, :email])
```

スカラー値はシンボル、配列は空配列 `[]`、ネストしたハッシュはハッシュ、と対応させるのが基本形です。

## マイグレーションで詰まる3つのパターン

### 既存データがあるテーブルに NOT NULL を付ける

開発初期は空のテーブルなので成功するマイグレーションが、本番やステージングのデータがある環境では失敗します。

```ruby
# 既存レコードが1件でもあると失敗する
class AddUserIdToComments < ActiveRecord::Migration[7.1]
  def change
    add_column :comments, :user_id, :integer, null: false
  end
end
```

エラーはこう出ます。

```
ActiveRecord::StatementInvalid: PG::CheckViolation: ERROR: column "user_id" of relation "comments" contains null values
```

対処は「カラム追加 → 既存データを埋める → NOT NULL 制約を付ける」の3ステップに分けることです。1つのマイグレーションで全部やろうとしないのがコツです。

```ruby
class AddUserIdToComments < ActiveRecord::Migration[7.1]
  def up
    add_column :comments, :user_id, :integer
    execute "UPDATE comments SET user_id = 1 WHERE user_id IS NULL" # 実際は適切な値を入れる
    change_column_null :comments, :user_id, false
    add_index :comments, :user_id
  end

  def down
    remove_index :comments, :user_id
    remove_column :comments, :user_id
  end
end
```

`up` / `down` を明示的に書くのは、`execute` を使った部分を Rails が自動で逆変換できないためです。`change` だけで済む単純な変更と、ロールバックを手書きする必要がある変更を見分けてください。

### インデックス作成で本番がロックされる

PostgreSQL で通常の `add_index` を実行すると、作成中はテーブルへの書き込みがブロックされます。中規模以上のテーブルでは数分間ロックが続くことがあります。オンラインで張る場合は `algorithm: :concurrently` を使いますが、これはトランザクション内で実行できないため `disable_ddl_transaction!` が必要です。

```ruby
class AddIndexToArticlesUserId < ActiveRecord::Migration[7.1]
  disable_ddl_transaction!

  def change
    add_index :articles, :user_id, algorithm: :concurrently
  end
end
```

ただし `concurrently` は途中で失敗すると `INVALID` 状態のインデックスが残ります。その場合は次で強制削除してから張り直します。

```bash
psql -c "DROP INDEX CONCURRENTLY index_articles_on_user_id;"
```

### PendingMigrationError と migration の状態確認

```
ActiveRecord::PendingMigrationError: Migrations are pending. Run 'bin/rails db:migrate' to resolve this issue.
```

これは DB 側の `schema_migrations` テーブルとマイグレーションファイルの同期が取れていない状態です。まず状況を確認します。

```bash
rails db:migrate:status
# database: app_development
#   Status   Migration ID    Migration Name
#--------------------------------------------------
#     up     20240101000001  CreateArticles
#     down   20240102000002  AddUserIdToComments  ← 未適用
```

`down` になっているものだけを適用すればよく、原因を推測する必要はありません。すでに手で DB を変更してしまった場合は `schema.rb` と実 DB の差分に注意し、必要なら `rails db:schema:load` で作り直す判断も選択肢に入ります（データは消えるので本番では絶対に実行しないでください）。

## N+1 クエリを検出して潰す

### 症状をログで見つける

N+1 はエラーではないため、画面上は正常に見えます。しかし件数が増えるとページが急激に遅くなります。ログに同一の SQL が何度も並んでいたら、それが N+1 の合図です。

```
Article Load (1.2ms)  SELECT "articles".* FROM "articles"
User Load (0.8ms)  SELECT "users".* FROM "users" WHERE "users"."id" = 1
User Load (0.6ms)  SELECT "users".* FROM "users" WHERE "users"."id" = 2
User Load (0.5ms)  SELECT "users".* FROM "users" WHERE "users"."id" = 3
```

コントローラで `@articles = Article.all` とし、ビューで `@article.user.name` をループしていると、記事件数 + 1 回のクエリが飛びます。

### includes で先読みする

修正は `includes` で関連をまとめて取得するだけです。

```ruby
# 修正前: 1 + N 回
@articles = Article.all

# 修正後: 2 回（IN 句でまとめて取得）
@articles = Article.includes(:user)
```

`includes` は2本のクエリに分けて関連データをメモリ上で結合します。JOIN 1本で解決したい場合は `eager_load`、JOIN が必須の絞り込み（`where` で関連先の条件を指定する）なら `joins` を使い分けます。

```ruby
# 関連先の条件で絞り込みたいので JOIN が必要
@articles = Article.joins(:user).where(users: { active: true })
```

なお `joins` は関連先のカラムを SELECT しないため、この書き方のままビューで `article.user.name` を呼ぶと N+1 に戻ります。絞り込みが目的なら `includes` + `references` を併用するのが安全です。

```ruby
@articles = Article.includes(:user).where(users: { active: true }).references(:user)
```

### 検出を自動化する

目視での検出は限界があるので、開発環境ではツールを入れましょう。Gemfile に次を追加します。

```ruby
group :development do
  gem 'bullet'
end
```

```ruby
# config/environments/development.rb
config.after_initialize do
  Bullet.enable = true
  Bullet.bullet_logger = true
  Bullet.raise = false # true にすると N+1 発生時に例外を投げて即気付ける
end
```

Rails 7.1 以降なら `strict_loading` も使えます。関連が未ロードのままアクセスされた時点でエラーにしてくれるため、N+1 を「本番で初めて気づく」事故を減らせます。

```ruby
class Article < ApplicationRecord
  belongs_to :user, strict_loading: true
end
```

読み取り回数だけが問題で、関連の中身が不要な場合は `counter_cache` や `select` による部分読み込みも有効です。

```ruby
class Article < ApplicationRecord
  belongs_to :user, counter_cache: true # users.articles_count を維持する
end
```

## まとめ

Rails の debugging は「勘」ではなく「確認手順」で解けます。今回取り上げた内容を整理すると、次のようになります。

- ルーティングエラーは `rails routes` で実際の URL を確認し、`collection` / `member` の使い分けで定義を追加する
- マイグレーションは「カラム追加 → データ投入 → 制約追加」を1つずつ分け、インデックスは `algorithm: :concurrently` を検討する
- N+1 は `log/development.log` の SQL の繰り返しで検出し、`includes` で解消、開発環境では bullet と `strict_loading` で再発を防ぐ

そして共通する原則は、エラーメッセージを最後まで読み、`rails routes`・`db:migrate:status`・ログという「事実が取れるコマンド」で現状を確認してから手を動かすことです。推測で直すと別の場所が壊れることがほとんどですが、確認してから直せば修正は驚くほど短時間で終わります。次に同じエラーに遭遇したときは、ぜひこの順序を試してみてください。
