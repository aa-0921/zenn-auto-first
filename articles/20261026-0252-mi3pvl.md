同じコマンドを毎回手で打つと、スペルミスやオプション忘れで失敗し、作業が止まってしまい、無駄な時間を取っていました。特に大規模な変更や複数人が同時に作業すると、どの変更がまだステージングされていないか把握しにくく、余計なコミットが頻発してレビュー負荷が増えていました。こうした悩みを解決するのが、以下の Git コマンドです。 

## git add -pで変更内容を細かくステージング

以前は `git add .` で全体をステージングし、不要なファイル変更が混ざりやすく、レビューで指摘されることが多かった。 
```git add -p```
を使うと、ハンク単位で変更を選択でき、対話形式で好きな行だけをステージングできる。実際に使うと、余計な変更が減り、レビューがスムーズになり、コミットミスが大幅に減って作業効率が向上した。特に大規模なコードベースでは、数百行単位の変更を一括でステージングすると間違いが起きやすいが、ハンク単位で細かく選べることで、レビュー前に必ず確認できるようになる。

## git stashで一時的に変更を保管

開発途中で別のタスクに切り替えなければならず、現在の作業を保留したいことが多かった。 
```git stash push -m "work-in-progress"```
で変更を stash に保存し、`git stash pop` で戻すと、作業環境をそのままに復元できる。実際に使うと、コンテキストを失わずに別タスクに着手でき、作業の流れが断続なく、無駄な再作業を防げる。また、複数の stash をスタックできるため、重要な変更を複数保管しつつ、別タスクに集中できる点も便利だ。 

## git cherry-pickで特定のコミットを apply

過去に作成した便利なコミットを別のブランチに移植したいときに、全体をマージする手間が面倒だった。 
```git cherry-pick <commit-hash>```
で特定のコミットだけを新しいブランチに持ち込める。実際に使うと、必要な変更だけを素早く統合でき、マージ conflicts を最小限に抑え、リリーススケジュールが安定した。さらに、特定のバグfixや機能追加だけを別ブランチに持ち込むときに、無駄なコミットが増えないというメリットも得られる。 

## git rebase -iで履歴をきれいに整理

複数回のコミットで歴史が乱れ、レビューが困難になっていた。 
```git rebase -i HEAD~5```
で直近の 5 コミットを対話的に編集し、pick, squash, drop などで履歴を整理できる。実際に使うと、コミットがまとまり、レビューがスムーズになり、リポジトリの履歴がコンパクトで管理しやすくなる。特に機能実装の途中で行った実験的なコミットを削除したり、 squash してまとめたりすることで、clean な履歴が保てる。 

## git bisectでバグの原因を二分探索

バグがいつ入ったか特定できず、時間だけが無駄に過ぎていた。 
```git bisect start```
```git bisect bad```
```git bisect good```
```git bisect reset```
を使って二分探索し、`git bisect reset` で終了させる。実際に使うと、原因となったコミットを素早く特定でき、修正作業が短縮され、品質向上に直結した。特に大規模プロジェクトでは、数百コミットにわたる履歴の中から原因を探す手間が激減し、開発スピードが大幅に上がる。 

## git clean -fdxで作業ディレクトリをすっきり

ビルド artefacts や未追跡ファイルが溜まると、容量を圧迫し、エラーの原因になることがあった。 
```git clean -fdx```
で untracked のファイルやディレクトリを一括削除でき、`-d` オプションでサブディレクトリも削除できる。実際に使うと、クリーンな環境で作業でき、ビルド時間が短縮され、事故防止にもなる。定期的に実行することで、リポジトリの肥大化を防ぎ、スムーズなデプロイが可能になる。 

## git push --force-with-leaseで安全に履歴を書き換える

リベースやブランチのリベースで歴史を書き換えると、他メンバーとのプッシが衝突しやすくなるリスクがあった。 
```git push --force-with-lease```
は安全に強制プッシでき、`--force-with-lease` がリモート側の最新 commit があるか確認してからプッシするため、誤って他者の作業を上書きしにくい。実際に使うと、履歴改変が安全に行えて、チーム開発の円滑さが保たれた。特に CI/CD パイプラインと連携させるときにも安心して使用できる。 

## git fetch --pruneでリモートブランチを整理

リモートに削除されたブランチが残っていると、`git branch -a` で一覧が膨らみ、操作が遅くなることがあった。 
```git fetch --prune```
で remote‑tracking ブランチを自動削除でき、`git remote prune origin` でも同様にできる。実際に使うと、ブランチ一覧がすっきりし、checkout が速くなり、リポジトリの健康状態が保たれた。定期的に実行すると、古いリモート参照が消え、コマンドの実行速度が向上する。
