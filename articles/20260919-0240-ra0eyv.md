Rails.application.routes.draw do

この状態で `GET /articles` にアクセスすると、当然ながらルーティングエラーが発生します。正しい定義は以下の通りです。

```ruby
# config/routes.rb（正しい例）
Rails.application.routes.draw do
  resources :articles
end
```

`resources :articles` を定義すると、`index`, `show`, `new`, `create`, `edit`, `update`, `destroy` の7つのRESTfulルートが一括で生成されます。なお、カスタムアクションを追加したい場合は `member` や `collection` ブロックを活用しましょう。

```ruby
Rails.application.routes.draw do
  resources :articles do
    member do
      get 'preview'  # /articles/:id/preview が追加される
    end
  end
end
```

デバッグのコツとしては、`rails routes` コマンドを実行して、定義されているルート一覧を確認することが最も確実です。エラーメッセージに登場するパスが、実際にroutes.rbに存在するかを必ず確認する習慣をつけましょう。

## マイグレーションエラー：テーブルが存在しない or カラムが足りない

マイグレーションエラーもまた、Rails初心者がよく遭遇する問題です。代表的なエラーメッセージとして `PG::UndefinedTable: ERROR: relation "articles" does not exist` や `ActiveRecord::StatementInvalid: Mysql2::Error: Unknown column 'status' in 'where clause'` があります。

これらのエラーは、大きく分けて2つの原因で発生します。1つ目はマイグレーションファイルを作成した後に `rails db:migrate` を実行していないケースです。例えば、新しい `articles` テーブルを作成するために以下のようなマイグレーションファイルを生成したとします。

```bash
rails generate migration CreateArticles title:string body:text
```

このとき、マイグレーションファイルは `db/migrate/20240101000000_create_articles.rb` として生成されますが、ここで `rails db:migrate` を実行せずにサーバーを起動してしまうと、データベースにテーブルが存在しないためエラーになります。

```ruby
# db/migrate/20240101000000_create_articles.rb
class CreateArticles < ActiveRecord::Migration[7.0]
  def change
    create_table :articles do |t|
      t.string :title
      t.text :body
      t.timestamps
    end
  end
end
```

解決策はシンプルで、`rails db:migrate` を実行してデータベースのスキーマを最新の状態に同期させることです。開発環境で不明な場合は `rails db:schema:load` を使って、`schema.rb` から一括でテーブル構造を作成することも有効です。

2つ目の原因は、既存のテーブルに必要なカラムが追加されていないケースです。例えば、記事に `status` カラムを追加したい場合、以下のように新しいマイグレーションを生成します。

```bash
rails generate migration AddStatusToArticles status:string
```

```ruby
# db/migrate/20240102000000_add_status_to_articles.rb
class AddStatusToArticles < ActiveRecord::Migration[7.0]
  def change
    add_column :articles, :status, :string, default: 'draft'
  end
end
```

このマイグレーションを実行した後にモデル側のバリデーションやビュー側のフォームを更新しないと、整合性の問題が発生します。マイグレーション実行後に必ず `rails db:migrate:status` で移行状況を確認し、`up` と `down` が正しく揃っているかをチェックする癖をつけましょう。

## N+1問題：パフォーマンスの最大の敵

N+1問題は、Railsアプリケーションのパフォーマンス低下を引き起こす最も凶悪な問題の一つです。これは、アソシエーションを使ってデータを取得する際に、親レコードの数だけ子レコードのクエリが余計に発行されてしまう現象です。

具体例で考えてみましょう。`Article` モデルが複数の `Comment` を持つ関係にある場合、以下のようなコードを書くとN+1問題が発生します。

```ruby
# コントローラー
def index
  @articles = Article.all
end
```

```erb
<!-- ビュー -->
<% @articles.each do |article| %>
  <h2><%= article.title %></h2>
  <% article.comments.each do |comment| %>
    <p><%= comment.body %></p>
  <% end %>
<% end %>
```

このコードでは、まず `Article.all` で1回のクエリが発行され、その後、記事1つ1つに対して `article.comments` が実行されるたびに追加のクエリが発行されます。記事が100件あれば、合計101回のクエリが発生することになります。これではデータベースの負荷が非常に大きくなり、ページの読み込みが遅くなります。

解決策は `includes` メソッドを使ったプリロードです。

```ruby
# コントローラー（改善版）
def index
  @articles = Article.includes(:comments).all
end
```

これにより、`Article` の取得クエリと `Comment` の取得クエリがそれぞれ1回ずつ、計2回のクエリにまとめられます。`includes` の代わりに `preload` や `eager_load` を使うこともできますが、基本的な考え方は同じです。

N+1問題のデバッグには、`bullet` というGemが非常に便利です。`Gemfile` に以下を追加してインストールします。

```ruby
gem 'bullet', group: :development
```

設定を有効にすると、開発モードでN+1クエリが発生した際にブラウザやログに警告を出してくれるため、気づかないうちにパフォーマンスが劣化するのを防ぐことができます。

## まとめ

Rails開発におけるよくあるエラーは、ルーティング・マイグレーション・N+1問題の3つが特に頻度が高いと言えます。これらのエラーに直面したときの対処法をまとめると以下の通りです。

- ルーティングエラーが発生したら、まず `rails routes` を実行して定義状況を確認する
- マイグレーションエラーが発生したら、`rails db:migrate` が実行済みかを `rails db:migrate:status` で確認する
- N+1問題が疑われる場合は、`includes` メソッドでクエリを最適化し、`bullet` Gemで警告を受け取る

これらのエラーは、Railsの基本的な仕組みを理解していれば回避・解決が容易です。日頃からエラーメッセージを読み解く練習を積み重ね、デバッグスキルを磨いていきましょう。
