同じコードをチェックしてもらうたびに「命名が統一されていない」「スペースの抜けがある」「コメントが不足している」といった指摘が繰り返されることに悩んでいた。ベテランエンジニアになるにつれて、レビューで同じ欠点を何度も指摘されることがストレスになり、効率的な解決策を探し始めることになった。

## 1. 変数の命名ルールが守られていない
**困っていたこと:** チームで使用する変数名がファイルごとにバラバラで、レビューアが都度修正を要求するため、コードの可読性が低下していた。
**具体的な使い方:**
```json
// .eslintrc.json
{
  "rules": {
    "camelcase": "error"
  }
}
npx eslint src/ --fix
```
**変ったこと:** ESLint の camelcase ルールを適用したことで、自動修正が適用され、レビューで命名に関する指摘が減り、コードの統一が容易になった。

## 2. インデントやスペースの抜け
**困っていたこと:** 手動で整頓していたが、ブラッシュアップするたびに空白文字が不均一になり、レビュアーがフォーマットに関する指摘を繰り返していた。
**具体的な使い方:**
```json
// package.json
{
  "scripts": {
    "format": "prettier --write src/"
  }
}
npm install prettier --save-dev
npm run format
```
**変ったこと:** Prettier による一括フォーマットで、インデントやスペースが統一され、レビュアーの指摘が減り、コミットメッセージもクリーンになった。

## 3. 複雑なロジックへのコメント不足
**困っていたこと:** ビジネスロジックが複雑な部分にコメントがなく、レビューアから「なぜこの処理をするのか」と質問されることが多かった。
**具体的な使い方:**
```bash
npm install jsdoc eslint-plugin-jsdoc --save-dev
npx jsdoc -c jsdoc.conf.json
npx eslint --fix
```
**変ったこと:** jsdoc と eslint-plugin-jsdoc を組み合わせることで、自動的にコメントを生成し、レビュー時の質問が減り、ドキュメントの品質が向上した。

## 4. テストの不足とカバレッジの低さ
**困っていたこと:** ユニットテストの割合が低く、レビューアから「カバレッジを上げてください」と指摘され、テスト作成に時間を取られていた。
**具体的な使い方:**
```json
// jest.config.json
{
  "coverageThreshold": {
    "global": { "branches": 80, "functions": 80, "lines": 80, "statements": 80 }
  }
}
npm install jest @jest/coverage-istanbul --save-dev
npx jest --coverage
```
**変ったこと:** カバレッジの閾値を設定したことで、自然とテストを書くようになり、レビューの指摘が減り、安心してコードを書けるようになった。

## 5. 魔法の文字列（ハードコードされたリテラル）
**困っていたこと:** API エンドポイントやメッセージを直接文字列として埋め込むことが多く、レビューアから「定数として抽出してください」と指摘されていた。
**具体的な使い方:**
```bash
npm install jscpd --save-dev
npx jscpd src/
```
**変ったこと:** jscpd によるスキャンで重複する文字列を検出し、定数ファイルに抽出するようになり、レビューの指摘が減り、メンテナンス性が向上した。

## 6. 不要なコンソール.log の残存
**困っていたこと:** デバッグ用に追加した `console.log` を削除し忘れることがあり、レビューアから「本番環境でログ出力しないでください」と指摘されていた。
**具体的な使い方:**
```json
// .eslintrc.json
{
  "rules": {
    "no-console": "error"
  }
}
npx eslint --fix
```
**変ったこと:** no-console ルールを有効にしたことで、誤って残したログを自動的に削除できるようになり、レビューの指摘が減った。

## 7. 関数の長さと複雑さ
**困っていたこと:** 単一の関数が100行を超えることがあり、レビューアから「分割してください」と指摘され、リファクタリングに時間がかかっていた。
**具体的な使い方:**
```bash
npm install eslint-plugin-function-length --save-dev
// .eslintrc.json
{
  "plugins": ["function-length"],
  "rules": {
    "function-length/function-max-statements": [2, 50]
  }
}
npx eslint --fix
```
**変ったこと:** 関数長ルールを適用したことで、早期に警告が表示され、小さな関数に分割する習慣が身につき、レビューの負荷が軽くなった。

## 8. エラーハンドリングの不備
**困っていたこと:** try-catch を省略することがあり、レビューアから「例外を適切に処理してください」と指摘され、コードの信頼性が疑われていた。
**具体的な使い方:**
```bash
npm install eslint-plugin-promise --save-dev
// .eslintrc.json
{
  "plugins": ["promise"],
  "rules": {
    "promise/param-names": "error"
  }
}
npx eslint --fix
```
**変ったこと:** eslint-plugin-promise により、未処理の Promise エラーを検出し、適切な catch ブロックを追加するようになり、レビューの指摘が減った。

## 9. 依存関係の更新忘れ
**困っていたこと:** セキュリティ脆弱性やバージョンの古さがレビューアから指摘され、都度パッケージの更新を行う必要があった。
**具体的な使い方:**
```bash
npm install -g renovate
renovate
```
**変ったこと:** Renovate を導入したことで、プルリクエストが自動で作成され、古い依存関係が事前に検出され、レビュー時の指摘がほぼなくなった。

## 10. ドキュメントの不足
**困っていたこと:** API の使用方法がドキュメントに書かれておらず、レビューアから「ドキュメントを書いてください」と指摘され、都度 README を更新していた。
**具体的な使い方:**
```bash
npm install jsdoc --save-dev
npx jsdoc -c jsdoc.conf.json
```
**変ったこと:** jsdoc により自動で API ドキュメントを生成できるようになり、レビュー時のドキュメント不足の指摘が減り、プロジェクトの透明性が向上した。

## まとめ
コードレビューでよく指摘される10のポイントを、実際のツールやコマンドを使って改善する方法を紹介した。まずは1つ、ESLint や Prettier など簡単なものから試してみると、レビューの負荷が格段に軽くなるだろう。ぜひ実践して、快適な開発ライフを手に入れよう。
