毎回ブラウザの「要素を検証」を開いて手探りで CSS を書き換えたり、コンソールに大量の `console.log` を流して目的の値だけ探したり──そんな作業に時間を取られていませんか。現場で何度も繰り返した失敗から、今では「これさえあれば即座に原因が見える」と実感している 10 の手法をまとめました。

## 1. Chrome DevTools Elements パネルで DOM 検証が楽になった
**困っていたこと**: HTML ソースを見ても適用済みスタイルや計算済みレイアウトが分からず、試行錯誤で CSS を書き換えていた。  
**使い方**:  
```text
// DevTools を開くショートカット
// Mac: Cmd + Option + I
// Windows/Linux: Ctrl + Shift + I
```  
Elements パネルで要素をクリックすると、右側の *Styles* / *Computed* で最終的な値が即座に確認でき、ライブ編集で即反映される。  
**変化**: ブラウザ上でスタイルをその場で微調整し、正解を見つけてからコードに反映できるため、修正サイクルが 5 分→30 秒に短縮された。

## 2. Console の条件付きブレークポイントで特定の値だけ止める
**困っていたこと**: 大量のログの中で「ユーザー ID が 42 のときだけ止めたい」と思っても、手動でフィルタするのは現実的でない。  
**使い方**:  
```text
// Sources タブで対象行の行番号を右クリック → "Add conditional breakpoint"
// 条件式例:
user.id === 42
```  
条件を満たした瞬間だけ実行が停止し、スコープ内の変数をそのまま確認できる。  
**変化**: 不要な停止がゼロになり、目的の状態にピンポイントで到達できるようになった。

## 3. Sources パネルの「ブラックボックス」でサードパーティコードを非表示にする
**困っていたこと**: スタックトレースに `jquery.min.js` やバンドルされたベンダーコードが大量に混じり、自分のコードがどこにあるか見失う。  
**使い方**:  
```text
// Sources タブで除外したいファイルを右クリック → "Blackbox script"
```  
ブラックボックス化したファイルはスタックトレースから隠され、ステップ実行もスキップされる。  
**変化**: 自分のコードだけに集中でき、デバッグの迷子時間が大幅に減った。

## 4. Network タブの「Preserve log」とフィルタでリクエスト追跡が容易に
**困っていたこと**: ページ遷移やリダイレクトのたびにネットワークログがクリアされ、前のリクエストが見られない。  
**使い方**:  
```text
// Network タブ → "Preserve log" にチェック
// フィルタ入力例: "api/" で API だけ表示
```  
遷移後も全履歴が残り、フィルタで必要なリクエストだけ抽出できる。  
**変化**: 認証フローやリダイレクトチェーンを一発で確認でき、原因特定が数秒で完了する。

## 5. React DevTools でコンポーネントツリーと props を即座に確認
**困っていたこと**: `console.log(props)` を毎回仕込まないと現在の props が分からず、再レンダリングの原因が追えない。  
**使い方**:  
```bash
npm install --save-dev react-devtools
npx react-devtools
```  
ブラウザ拡張としてもインストール可能。コンポーネントツリー上で選択すると右ペインに props / state / hooks が表示される。  
**変化**: 再レンダリングのトリガーを視覚的に追跡でき、不要な再描画を即座に見つけられる。

## 6. Redux DevTools で状態履歴をタイムトラベルデバッグ
**困っていたこと**: アクション発行後の state 変化をコンソールで追うと、どのアクションがどの変化を生んだか把握しにくい。  
**使い方**:  
```js
// store 作成時に拡張を有効化
import { devToolsEnhancer } from '@redux-devtools/extension';
const store = createStore(rootReducer, devToolsEnhancer());
```  
DevTools パネルでアクション履歴をクリックすると、その時点の state にジャンプできる。  
**変化**: 「あのバグ、どのアクションで起きた？」を過去に遡って即確認でき、修正検証が一瞬で終わる。

## 7. VS Code の launch.json で Chrome にアタッチし、ブレークポイントをエディタで操作
**困っていたこと**: ブラウザの DevTools とエディタを行き来してブレークポイントを設定するのが面倒。  
**使い方**:  
```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "chrome",
      "request": "launch",
      "name": "Launch Chrome",
      "url": "http://localhost:3000",
      "webRoot": "${workspaceFolder}"
    }
  ]
}
```  
`F5` で Chrome が起動し、VS Code 側のブレークポイントがそのまま効く。  
**変化**: エディタ上で変数ウォッチ・コールスタック確認が完結し、コンテキストスイッチがなくなった。

## 8. Source Map を有効にして minified コードを元の TypeScript にマッピング
**困っていたこと**: 本番ビルドのバンドルが難読化されており、エラースタックが読めない。  
**使い方**:  
```js
// webpack.config.js (または vite.config.ts)
module.exports = {
  // ...
  devtool: 'source-map',   // 本番でも source-map を出力
};
```  
ブラウザは自動的に `.map` を読み込み、元の TS/JS 行番号でスタックトレースを表示する。  
**変化**: 本番エラーの行番号がそのままソースコードに対応し、修正箇所を即特定できる。

## 9. Lighthouse CI でパフォーマンス・アクセシビリティを自動チェック
**困っていたこと**: 手動で Lighthouse を回すのを忘れ、リリース後にスコア低下に気づく。  
**使い方**:  
```bash
# CI スクリプトに追加
npx lhci autorun --upload.target=temporary-public-storage
```  
PR 毎にスコアがレポートされ、閾値未満なら失敗させられる。  
**変化**: パフォーマンス劣化をマージ前に検知でき、ユーザー体験の低下を未然に防げる。

## 10. Storybook の Controls と Docs で UI 単体の挙動を隔離確認
**困っていたこと**: ページ全体の中でしか確認できないコンポーネントの状態変化を、アプリ起動なしで試せない。  
**使い方**:  
```js
// Button.stories.tsx
export const Primary = {
  args: { label: 'Submit', disabled: false },
  argTypes: { disabled: { control: 'boolean' } },
};
```  
Storybook を起動 (`npm run storybook`) すると、Controls パネルで props を動的に切り替えられる。  
**変化**: コンポーネント単体で全パターンを網羅的に確認でき、回帰バグが激減した。

## まとめ
ここに挙げた 10 の手法は、それぞれ「ある一点の手間」を劇的に減らしてくれます。まずは気になった 1 つだけ試してみて、デバッグのストレスがどれだけ軽くなるか体感してみてください。
