## コードレビューに臨む心構え

コードレビューは単なるバグ見つけではなく、チーム全体の知識共有と個人のスキル向上の場です。私が最初にレビューを受けたときは、指摘が自分への批判のように感じられ、防衛的になることが多かったです。しかし、レビューの目的を「コードの品質を上げる」ではなく「自分自身の考え方を広げる」と捉え直すと、気持ちが楽になりました。具体的には、レビュー前に以下の三点を意識しています。

1. **完璧を求めない** – 自分のコードが完璧である必要はなく、改善点を見つける機会だと考える。  
2. **フィードバックは贈り物** – 指摘してくれる人は時間を割いてくれている。感謝の気持ちを持つと受け止めやすくなる。  
3. **自分の考えを言語化する習慣** – レビュー前に「なぜこう書いたのか」を簡単にメモしておくと、質問されたときに答えやすくなる。

こうした心構えを持つだけで、レビュー中の緊張感が和らぎ、建設的な対話が生まれやすくなります。

## 指摘の受け止め方と質問の仕方

実際にレビューで指摘を受けたときの対応フローを、私の体験談を交えて紹介します。

### 1. 一旦立ち止まって感情を整理する

指摘が来たら、まずは深呼吸して「これは自分の能力を否定しているわけではない」と自分に言い聞かせます。感情が高ぶると、指摘の内容を見逃したり、誤解して反論しがちです。私は指摘が届いたら、まずはメモアプリに「指摘内容」と「最初の感情」を書き出し、5分ほど置いてから再読み直す習慣をつけています。

### 2. 指摘の意図を確認する

指摘が抽象的だったり、なぜその変更が必要なのか不明な場合は、丁寧に質問します。例えば：

```text
- この部分の命名について、なぜ「user_id」ではなく「uid」が良いと考えましたか？
- ここで例外処理を入れる理由は、どのようなシナリオを想定しているのでしょうか？
```

質問するときは「なぜ」ではなく「どのように」や「何を目的として」といった形にすると、相手も答えやすくなります。

### 3. 自分の考えを返す

質問の答えを得たら、自分の実装意図を簡潔に説明します。このとき、コードスニペットを提示すると伝わりやすいです。

```python
# 元の実装
def get_user(id):
    return db.query("SELECT * FROM users WHERE id = %s", (id,))

# レビュー後の改善案（提案された方向性に合わせて）
def get_user(id):
    try:
        return db.query("SELECT * FROM users WHERE id = %s", (id,)).fetchone()
    except DatabaseError as e:
        logger.error(f"Failed to fetch user {id}: {e}")
        raise
```

このように、指摘を受け入れる姿勢と自分の考えを示すプロセスを繰り返すことで、レビューは単なる指摘のやり取りではなく、共同での問題解決になります。

## レビューを成長の機会に変えるコツ

レビューから得られる学びを最大化するために、私が実践している具体的な習慣を紹介します。

### コードレビューのチェックリストを作る

レビュー前に自分用のチェックリストを用意すると、見落としが減ります。私のチェックリスト例は次の通りです。

- [ ] 関数・変数の命名がドメイン語と一致しているか  
- [ ] 例外処理は網羅しているか（特に外部API呼び出し時）  
- [ ] コメントは「なぜ」を説明しているか（何をしているかはコードでわかる）  
- [ ] テストケースは網羅的か（境界値と異常系を含むか）  
- [ ] パフォーマンスに影響しそうなループや再帰はないか  

このリストをレビュー前に一度見直すだけで、指摘されるポイントを事前に潰すことができます。

### レビュー後の振り返りを習慣化する

レビューが終わったら、5分程度の振り返りを書きます。書く内容は以下の三点です。

1. **何を指摘されたか** – 箇条書きでリスト化。  
2. **自分がどう対応したか** – 修正したコードや考え方の変化。  
3. **次回に活かせる教訓** – 同じミスを繰り返さないための具体的なアクション（例：命名規則のドキュメントを読む、ユニットテストのテンプレートを作るなど）。

この振り返りをリポジトリのWikiや個人のノートに残しておくと、時間が経っても学びを振り返りやすくなります。

### メンタル面での対処法

レビューで落ち込みやすいときは、以下の二つを意識しています。

- **小さな成功を記録する** – 「今日は指摘が2件しかなく、以前より減った」など、微細な進歩でもメモに残す。  
- **同僚と非公式に雑談する** – レビュー後の雑談で「今回の指摘はこう思った」など感想を共有すると、孤独感が薄れ、客観的にフィードバックを受け止めやすくなる。

## まとめ

コードレビューは技術的な指摘だけでなく、自分の考え方やメンタルを鍛える場でもあります。心構えを整え、指摘の受け止め方と質問の仕方を工夫し、レビュー後の振り返りとチェックリストで学びを体系化すれば、レビューは恐れるべき評価ではなく、成長の加速器になります。ぜひ今回紹介したフレームワークを試してみて、自分なりの「レビューを楽しむ」スタイルを見つけてみてください。
