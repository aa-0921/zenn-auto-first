## コミットメッセージを英語で適当に書くとレビューで地獄を見る

「fix」「update」「bug」だらけのコミットメッセージを送ったことがあります。レビュアーは何が変更されたのか理解できず、「詳細を書け」と指摘を受けました。日本語で具体的に書いた方がわかりやすいです。

```
# 良い例
feat: ユーザー登録画面のバリデーションを追加
fix: ログインエラー時のメッセージを修正
```

## ブランチを main に直接プッシュすると本番環境が壊れる

main ブランチに直接コードを書き込んでしまい、テストもせずにデプロイしていた時期がありました。一度でもミスすると本番環境全体が停止するため、フィーチャーブランチを切ってレビューを必ず通すようにしました。

```
git checkout -b feature/user-auth
# 作業後
git checkout main
git merge feature/user-auth
```

## 環境変数をハードコーディングすると本番で泣く

ローカル開発では動くのに本番では動かない問題を何度も経験しました。API キーやデータベース URL をコードに直書きしていたため、環境ごとに切り替えるたびに修正が必要でした。 `.env` ファイルで管理する習慣をつけました。

```
# .env
DB_HOST=localhost
API_KEY=your_api_key_here
```

## npm install をする前に package.json を確認すること

`npm install` したら予期せぬパッケージが大量に入り、プロジェクトが壊れたことがあります。 `package.json` を確認して依存関係を理解してからインストールすると安全です。

```
{
  "dependencies": {
    "express": "^4.18.0"
  }
}
```

## エラーメッセージを無視して進むとデバッグ地獄

エラーを無視してコードを書き進めると、後で謎のバグが発生しました。エラーメッセージは問題の手がかりなので、最初に解決する癖をつけると良いです。

```
console.log(error);
// エラーを読み解いて原因を特定する
```

## デプロイ前にローカルでしか動かないコードを本番に上げる

ローカルでは動作するのに、本番ではパスが違って動かないなどの問題を経験しました。デプロイ前に必ず本番環境に近い状態でテストする必要があります。

```
# 本番用設定ファイルを作成
NODE_ENV=production npm start
```

## データベースマイグレーションを手動で行うとデータが消える

マイグレーションファイルを直接編集してしまい、チームメンバーのデータベースが壊れたことがあります。マイグレーションは追加専用で、元に戻す手順も準備しましょう。

```
npx sequelize-cli migration:generate --name add-user-table
npx sequelize-cli db:migrate
```

## コードレビューを怠 neglect するとチーム開発が止まる

コードレビューを放棄すると、バグが積み重なり最後には大きな問題になりました。レビューはチーム全体の品質を保つ重要なプロセスです。

```
# Pull Request にレビュアーを指定
git push origin feature/new-feature
# GitHub で PR を作成しレビューを依頼
```

## ドキュメントを書かないと自分もわからない

数日後に自分の書いたコードを見直したことがありますが、何をしているのか全くわかりませんでした。コメントや README を書くことで、将来の自分も助かります。

```
# README.md
## セットアップ
npm install
npm run dev
```

## まとめ

失敗は誰も避けられないものですが、それを繰り返さないように記録しておくことが大切です。駆け出しのうちにこれらの失敗を知っていれば、時間とストレスを節約できます。まずは 1 つ試してみてほしいですね。
