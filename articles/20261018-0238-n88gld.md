## Git 初期設定とコミ tacticを最初に決める

困ったこと：git initしたあと、どうコミットしていくか迷っていました。trunk-styleかfeature branchか、最初に決めないと後でgit rebaseやgit mergeを振り返りづらくなります。trunk-styleにしたほうがシンプルに始められます。

使い方：初期コミットを作る際の設定とコミット方法です。

```bash
git init
git config user.name "yourname"
git config user.email "you@example.com"
git commit -m "initial commit"
```

使ってみて：初期コミットの戦術が明確になったおかげで、後でgit rebase interactiveやgit cherry-pickを振り返りやすくなりました。trunk-styleにしておけば、feature branchを切りたいときにすぐ切れます。

## プロジェクトの言語を最初に決める

困ったこと：Web開発を始めるのにJavaScriptとTypeScriptで迷っていました。型定義があるかないかで後でかなりの違いが出ます。TypeScriptにしたほうが後でバグが少なくなりますが、最初に覚えることが多すぎて挫折しそうになりました。

使い方：TypeScriptプロジェクトの初期設定です。

```bash
npm create vite@latest my-app -- --template typescript
cd my-app
```

使ってみて：型定義のおかげで後でバグが出にくくなり、コードの保守性が上がりました。最初に言語を決めておけば、後で大幅な移管をする必要がなくなりました。

## CI/CDツールを最初に入れる

困ったこと：GitHub ActionsやCircleCIを後回しにしていたらいろんなことが不便になりました。ビルドとテストを自動化しないと、修正翣が怖くてなかなかコードを書けません。CIなしで開発を続けるのはかなり厳しいです。

使い方：GitHub Actionsの初期設定(.github/workflow/ci.yml)です。

```yaml
name: CI
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm ci
      - run: npm test
```

使ってみて：コミするたびにテストが走るようになり、安心してコードを書けるようになりました。CIが通っているかどうかを確認する手間がなくなります。

## テストの書き方方針を最初に決める

困ったこと：TDPとTDDの違いがわからず、テストを書くか書かないかで迷っていました。TDPならまずテストを書かないと宣言できませんが、テストを書くことに抵抗がありました。TDDにすると最初は辛いですが、後で大きな助けになります。

使い方：TDPを宣言してテストを書く方法です。

```typescript
describe('add', () => {
  it('returns 3 when adding 1 and 2', () => {
    expect(add(1, 2)).toBe(3);
  });
});
```

使ってみて：テスト先行で書くことで、バグの原因が明確になり、修正もしやすくなりました。TDDにしておけば、後でリファアップがスムrldになるというメリットもあります。

## デバッグツールを最初に選ぶ

困ったこと：print文でデバッグしていましたが、巨大なログを出力するのに辟きでした。デバッグに時間を取られてしまいます。 print文を多用していると、バグの原因が見つかりにくいだけでなく、コードの可読性も落ちます。

使い方：Node.jsでDebuggerを使う方法です。

```javascript
function add(a, b) {
  debugger; //ブレポイントを入れる
  return a + b;
}
```

使ってみて：ブレポイントで止まって確認できるようになり、print logを書く手間が省けました。デバッグが効率化することで、修正案が速くなりました。

## 静エラーチェッティングツールを最初に入れる

困ったこと：バグが発生しても原因がわからず、デバッグにかなりの時間を取っていました。静的エラーチェッティングツールを入れると未然に防げます。静的エラーが早い段階で見つかれば、修正工数を大幅に減らせます。

使い方：ESLintの初期設定です。

```bash
npm install eslint --save-dev
npx eslint .
```

使ってみて：静的エラーが早い段階で見つかるようになり、修正工数が減りました。eslintrcを最初に入れておけば、後でルールを追加するのも簡単です。

## 依イヤー管理ツールを最初に選ぶ

困ったこと：node_modulesが肥大化していて、依存関係が複雑になっていました。最新版のパップンが安定しなかったり、package-lock.jsonが壊れることがありました。pnpmを入れることでキャレット管理が効率化されます。

使い方：pnpmでキャレット管理を行う設定です。

```bash
npm install pnpm -g
pnpm add eslint prettier
```

使ってみて：キャレット管理が効率化され、依存関係が整理され、再現性が上がりました。pnpmを使うとdisk spaceも節約できます。

## まとめ

個人開発を始める前に決めておくと楽になることは多いです。Git tactic、言語、CI/CD、テスト方針、デバッグツール、静的エラーチェッティング、 依イヤー管理ツールの7つを最初に決めると、後で混乱しなくてすみます。まずは1つだけ試してみてください。
