## Dockerの基本概念：イメージとコンテナの違い
### イメージとは
イメージは、アプリケーションを実行するために必要なファイルシステム、ライブラリ、環境変数などを読み込み専用のレイヤーとしてまとめたテンプレートです。Dockerfileに記述した手順に従って`docker build`コマンドで作成されます。イメージは変更不可（immutable）であり、同じイメージから何個でもコンテナを起動できます。

### コンテナとは
コンテナは、イメージをベースに作成される実行可能なインスタンスです。起動時に書き込み可能なレイヤーが追加され、アプリケーションの実行状態や一時ファイルがここに書き込まれます。コンテナは隔離されたプロセス空間で動くため、ホストOSに影響を与えずに複数の異なる環境を同時に走らせられます。

#### 例：シンプルなNode.jsアプリのDockerfile
```dockerfile
# ベースイメージ
FROM node:18-alpine

# 作業ディレクトリを設定
WORKDIR /app

# package.json と package-lock.json をコピー
COPY package*.json ./

# 依存関係をインストール
RUN npm ci --only=production

# アプリケーションソースをコピー
COPY . .

# ポート3000を公開
EXPOSE 3000

# 起動コマンド
CMD ["node", "index.js"]
```
このDockerfileから`docker build -t my-node-app .`とすると、`my-node-app`という名前のイメージが生成されます。続いて`docker run -p 3000:3000 my-node-app`でコンテナを起動すれば、ホストのポート3000からアプリにアクセスできます。

## docker-composeの基本と実践例
複数のコンテナ（たとえばウェブサーバーとデータベース）を連携させたい場合、毎回長い`docker run`コマンドを書くのは煩雑です。そこで登場するのが`docker-compose`です。YAML形式でサービス、ネットワーク、ボリュームを宣言的に定義し、`docker-compose up`一つで全体を起動できます。

### docker-compose.ymlの構成例
```yaml
version: "3.9"

services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=development
    volumes:
      - .:/app
      - /app/node_modules   # ボリュームでホストのnode_modulesをマウントしない
    depends_on:
      - db

  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"

volumes:
  pgdata:
```
- `web`サービスは現在ディレクトリのDockerfileからイメージをビルドし、ホストのポート3000にマッピングします。
- `db`サービスは公式Postgresイメージを使い、データを永続化するために名前付きボリューム`pgdata`を割り当てます。
- `depends_on`でウェブがデータベースより後に起動するように順序付けしています（厳密な待機はアプリ側でリトライロジックを実装）。

### 使い方
```bash
# ビルドと起動
docker-compose up --build

# バックグラウンドで起動
docker-compose up -d

# 停止とリソース解放
docker-compose down
```
`docker-compose up`を実行すると、定義されたサービスが順に起動し、ログがターミナルに流れます。`-d`オプションでデタッチドモードにすれば、バックグラウンドで動かし続けられます。

## ローカル開発でDockerを使うメリット
1. **環境の再現性**  
   Dockerfileとdocker-compose.ymlさえあれば、どのマシンでも同じバージョンの言語ランタイムやミドルウェアをインストールできます。「うちのマシンでは動くのに…」という問題が劇的に減ります。

2. **依存関係の隔離**  
   各プロジェクトごとに独立したコンテナ内で依存パッケージを管理するため、グローバルなパッケージ衝突やバージョンロックの心配がなくなります。たとえば、プロジェクトAがNode 16、プロジェクトBがNode 18を必要としても、それぞれのコンテナ内で解決できます。

3. **スピーディーなオンボーディング**  
   新メンバーが参加したとき、`git clone`後に`docker-compose up --build`だけで開発環境が整います。長いセットアップドキュメントや手順書を読む必要がなくなり、すぐにコードを書き始められます。

4. **CI/CDとの親和性**  
   ローカルで使っている同じイメージをGitHub ActionsやGitLab CIなどのCIパイプラインに流用すれば、「ローカルとCIで動作が違う」というトラブルを防げます。テストステージでも同じコンテナを使えば、結果の再現性が高まります。

5. **リソースのクリーンアップ**  
   開発が終わったら`docker-compose down -v`でボリュームも含めてコンテナと関連リソースを一掃できます。ホストOSに残るゴミファイルが少なく、システムが快適に保たれます。
