プルリクエストを出すたびに「変数名がわかりにくい」「マジックナンバーを定数にして」「エラーハンドリングが足りない」といった指摘が返ってきて、修正コミットを積み重ねる日々が続いていた。レビュー待ちの時間が長くなり、自分のタスクが進まないもどかしさを感じていた。そこで、自分がレビューされる側・する側の両方で頻出する指摘を整理し、手元で防げる仕組みを導入してみた。以下の10項目を意識するだけで、指摘数が激減し、レビューが「LGTM」で終わることが増えた。

## 1. 変数名・関数名が曖昧で意図が伝わらない
一時的な変数に `data` や `temp`、処理内容が想像できない `handleClick` などを使い回していた。レビュアーから「何を入れているのかわからない」「責務が読み取れない」と毎回指摘され、命名に悩む時間が長かった。ESLint の `id-length` や `id-denylist` ルールで短すたり禁止語を検知させ、命名規約を強制した。

```json
// .eslintrc.js
rules: {
  "id-length": ["error", { "min": 2, "exceptions": ["i", "j", "k"] }],
  "id-denylist": ["error", "data", "temp", "info", "val", "obj", "item"]
}
```

命名に迷う時間が減り、レビューで「ここは `userList` の方がいい」といった微調整だけで済むようになった。コードリーディングの負荷も下がり、自分で読み返しても意図がすぐわかる。

## 2. マジックナンバーが散らばり保守性が下がる
ステータスコード `200` やリミット値 `50`、ピクセル値 `16` などをベタ書きしていた。仕様変更で値を変える際に漏れが出たり、「この数字の意味は？」と聞かれたりするたびにgrepで探す手間があった。定数ファイルにまとめ、用途ごとに命名して export する運用に変えた。

```ts
// src/constants/http.ts
export const HTTP_STATUS = {
  OK: 200,
  CREATED: 201,
  BAD_REQUEST: 400,
  UNAUTHORIZED: 401,
  NOT_FOUND: 404,
  INTERNAL_SERVER_ERROR: 500,
} as const;

// 使用側
if (response.status === HTTP_STATUS.OK) { ... }
```

値の意味がコード上で自己完結し、変更時も一箇所直せば済む。レビューで「マジックナンバーです」と言われることがゼロになり、仕様書とコードの乖離も防げるようになった。

## 3. エラーハンドリングが雑でクラッシュの原因に
`try-catch` を書かずに `await` だけ並べたり、catch で `console.error` だけして握りつぶしたりしていた。本番でネットワークエラーが起きたときに画面がフリーズし、原因特定に時間を取られた。共通のエラーハンドラを用意し、API 呼び出しは必ずラップする形に統一した。

```ts
// src/utils/withErrorHandling.ts
export async function withErrorHandling<T>(
  promise: Promise<T>,
  fallback: T,
  onError?: (e: unknown) => void
): Promise<T> {
  try {
    return await promise;
  } catch (e) {
    onError?.(e);
    return fallback;
  }
}

// 使用側
const user = await withErrorHandling(fetchUser(id), null, (e) => logger.error(e));
```

例外が握りつぶされず、フォールバック値で UI が壊れない。レビューで「エラー時の挙動は？」と聞かれず、Sentry などの監視ツールにも確実に飛ぶようになった。

## 4. 関数が長すぎてテストしにくい
1 関数 100 行超えの「神関数」を書きがちで、条件分岐がネストして可読性が最悪だった。単体テストを書こうとしてもモックの準備が大変で、結局テストをサボる悪循環だった。責務ごとにプライベート関数やカスタムフックへ切り出し、1 関数 20 行以内を目安にリファクタリングした。

```ts
// Before: 100行の巨大関数
async function processOrder(order: Order) { ... }

// After: 責務分割
function calculateTotal(items: Item[]): number { ... }
function validateStock(items: Item[]): ValidationResult { ... }
async function chargePayment(amount: number): Promise<PaymentResult> { ... }
async function sendConfirmationEmail(order: Order): Promise<void> { ... }

export async function processOrder(order: Order) {
  const total = calculateTotal(order.items);
  const validation = validateStock(order.items);
  if (!validation.ok) throw new Error(validation.message);
  const payment = await chargePayment(total);
  await sendConfirmationEmail({ ...order, paymentId: payment.id });
}
```

各関数が純粋になり、ユニットテストが書きやすくなった。レビューでも「この関数何してるの？」という質問が減り、バグ混入リスクも下がった。

## 5. コメントアウトされたコードが残りノイズになる
「あとで戻すかも」と `//` で残したコードが数ヶ月放置され、差分が読みにくくなっていた。レビュアーから「消してください」と言われるたびに手動で削除していた。Git の履歴で戻せることを徹底し、コミット前に `git diff --check` や IDE の「未使用コード検出」で強制削除する習慣をつけた。

```bash
# コミット前のフック例
# .git/hooks/pre-commit
#!/bin/sh
if git diff --cached --check | grep -q '^\+.*//'; then
  echo "コメントアウトコードが含まれています。削除してください。"
  exit 1
fi
```

リポジトリがクリーンになり、レビュー時のノイズが消えた。「このコード生きてる？」という確認コストがゼロになり、Git 履歴を信頼して開発できるようになった。

## 6. デバッグ用の console.log が本番に混入
開発中に `console.log('here')` や `console.dir(user)` を仕込み、消し忘れてデプロイしてしまうことが多かった。本番コンソールが汚れ、セキュリティ的にも良くないと指摘された。ESLint の `no-console` ルールを `warn` ではなく `error` にし、許可するのは独自ロガー経由のみに制限した。

```json
// .eslintrc.js
rules: {
  "no-console": ["error", { "allow": ["warn", "error"] }]
}

// src/utils/logger.ts
export const logger = {
  debug: (...args: unknown[]) => process.env.NODE_ENV === 'development' && console.debug(...args),
  info:  (...args: unknown[]) => console.info(...args),
  warn:  (...args: unknown[]) => console.warn(...args),
  error: (...args: unknown[]) => console.error(...args),
};
```

CI で弾かれるため、消し忘れが物理的に不可能になった。本番コンソールがきれいになり、ログ集約ツールへの連携もスムーズになった。

## 7. any 型の乱用で型安全性が損なわれる
外部 API のレスポンスや複雑なオブジェクトに `any` をつけて「あとで直す」と言って直さないままマージしていた。実行時エラーが出てから型不整合に気づく羽目になり、デバッグに時間を溶かしていた。`no-explicit-any` を `error` にし、不明な型は `unknown` や Zod スキーマでバリデーションしてから絞り込むフローを徹底した。

```json
// .eslintrc.js
rules: {
  "@typescript-eslint/no-explicit-any": "error"
}
```

```ts
// Zod で実行時検証＆型推論
import { z } from 'zod';
const UserSchema = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof UserSchema>;

const raw = await fetchUser(id);
const user = UserSchema.parse(raw); // 型安全 & 実行時保証
```

`any` が消え、コンパイル時にバグを検知できるようになった。レビューで「ここ any だけど大丈夫？」という会話がなくなり、リファクタリング時の安心感が段違いに上がった。

## 8. ネストが深く可読性が悪い（アロー関数地獄）
コールバック地獄や `if` のネストが 4〜5 段になり、横スクロール必須のコードを書いていた。早期リターン（Guard Clauses）と `Array` メソッド、`Promise.all` などでフラットに書き換えるよう意識した。

```ts
// Before: ネスト地獄
function getActiveUsers(users: User[]) {
  return users.filter(u => {
    if (u.isActive) {
      if (u.lastLogin > Date.now() - 86400000) {
        return u.posts.some(p => p.published);
      }
    }
    return false;
  });
}

// After: Guard Clauses + メソッドチェーン
function getActiveUsers(users: User[]) {
  const recentThreshold = Date.now() - 86400000;
  return users
    .filter(u => u.isActive)
    .filter(u => u.lastLogin > recentThreshold)
    .filter(u => u.posts.some(p => p.published));
}
```

認知負荷が下がり、バグを見逃さなくなった。レビューで「ネスト深すぎ」と言われず、ロジックの流れが上から下へ読めるようになった。

## 9. テストコードがなくリグレッションが怖い
機能追加のたびに手動確認のみで PR を出し、後から別機能の修正で壊れて気づくことが多かった。レビュアーから「テスト書いてください」と言われ、その場しのぎで書く羽目に。Vitest と Testing Library を導入し、新規機能には必ずテストを同梱するルールを CI で強制した。

```ts
// src/features/auth/__tests__/login.test.ts
import { render, screen, fireEvent } from '@testing-library/react';
import { LoginForm } from '../LoginForm';
import { userEvent } from '@testing-library/user-event';

test('正しい認証情報でログイン成功', async () => {
  const user = userEvent.setup();
  render(<LoginForm onSubmit={vi.fn()} />);
  await user.type(screen.getByLabelText('メール'), 'test@example.com');
  await user.type(screen.getByLabelText('パスワード'), 'password123');
  await user.click(screen.getByRole('button', { name: 'ログイン' }));
  // アサーション...
});
```

リグレッションが CI で即検知されるようになり、安心してリファクタリングできる。レビューでも「テストパスしてるね」で終わることが増え、信頼残高が貯まった。

## 10. PR が巨大でレビューに時間がかかる
機能単位でコミットをまとめず、1 PR に複数の機能・リファクタ・設定変更を混ぜて 500 行超えの差分を出していた。レビュアーの負担が大きく、指摘漏れやマージコンフリクトが頻発した。1 PR 1 機能・200 行以内を目安に、依存関係のない変更は別 PR に分割する運用にした。

```bash
# 作業ブランチを細かく切る例
git checkout -b feat/login-ui
# ...実装・コミット
git push -u origin feat/login-ui
# PR 作成 → レビュー → マージ

git checkout main
git pull
git checkout -b feat/login-api
# ...実装・コミット
```

レビュー待ち時間が短縮され、コンフリクトも激減。レビュアーから「小さくてレビューしやすい」と言われるようになり、マージまでのリードタイムが半分以下になった。

## まとめ
ここで紹介した 10 のポイントは、特別なツールや難しいテクニックではなく「今のプロジェクトにすぐ導入できるルールと設定」ばかりだ。まずは ESLint の `no-console` や `no-explicit-any` を `error` にするなど、1 つだけでも試してみてほしい。小さな積み重ねが、レビューの質と開発スピードを確実に変えてくれる。
