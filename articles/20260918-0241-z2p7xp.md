## 導入：なぜ型を付けたのにエラーが減らないのか

TypeScriptを始めたばかりの頃、「コンパイルは通るのに、実行するとデータが missing だった」「何でも代入できる `any` を多用していたら、結局JavaScriptと同じになった」と感じることはないでしょうか。

TypeScriptの型は、単に変数にラベルを付けるためのものではありません。実行前に「この値は文字列として扱ってよいのか」「このプロパティは本当に存在するのか」「関数が返す値をそのまま表示してよいのか」を確認するための仕組みです。

この記事では、型の推論、ユニオン型、オプションのプロパティ、`any` と `unknown` の違いを具体例で解説します。最後に、実務で型定義を書くときの手順も紹介します。

## まず押さえたい「型の推論」と明示的な型注釈

TypeScriptでは、初期値から型を自動的に判断できます。これを**型の推論**と呼びます。

```ts
let quantity = 1;

quantity = 2;     // OK: number
quantity = "2";   // エラー: string は number に代入できない
```

`quantity` は初期値 `1` から `number` 型だと推論されます。そのため、文字列を代入するとエラーになります。

一方、関数の引数や戻り値には、原則として型注釈を付けるのが分かりやすい方法です。

```ts
function formatPrice(price: number, currency = "JPY"): string {
  return `${currency} ${price.toLocaleString("ja-JP")}`;
}

formatPrice(1980);       // "JPY 1,980"
formatPrice("1980");     // エラー
```

引数に `price: number` を指定しているため、文字列を渡した段階でミスに気付けます。戻り値の `: string` は省略しても推論できますが、公開する関数や複雑な処理では明示すると意図が伝わりやすくなります。

ここで重要なのは、**必要以上に型を書かないこと**です。ローカルな変数まで毎回 `let count: number = 0` と書くより、推論に任せた方が可読性が上がる場合があります。型の推論で十分なら任せ、関数の境界や外部から受け取る値では明示する、という使い分けが基本です。

## オブジェクトの型定義では「存在しないプロパティ」を想定する

ユーザー情報を扱う場合、次のように型を定義できます。

```ts
type User = {
  id: number;
  name: string;
  email?: string;
  role: "admin" | "member";
};

const admin: User = {
  id: 1,
  name: "山田太郎",
  email: "taro@example.com",
  role: "admin",
};

const guest: User = {
  id: 2,
  name: "ゲスト",
  role: "member",
};
```

`email?: string` は、「email が常に文字列」とは限らず、**プロパティ自体が存在しなくてもよい**ことを表します。したがって、何も確認せずに使うことはできません。

```ts
function getContactLabel(user: User): string {
  return user.email ?? user.name;
}
```

`??` を使えば、`email` が `undefined` のときに `name` を代替値にできます。

なお、`email: string | null` と `email?: string` は同じ意味ではありません。

- `email?: string`：プロパティが存在せず、値は `string | undefined` として扱われる
- `email: string | null`：プロパティは存在するが、値が `null` の場合もある

APIの仕様で明示的に `null` が返ると決まっているなら `string | null`、送信時だけ省略できる項目なら `email?: string` が適している場合があります。実データとAPI仕様を確認せずに直感で決めるのは避けましょう。

## ユニオン型とナローイング：条件分岐で型を絞り込む

複数のパターンを1つの型として表現するには、**ユニオン型**を使います。

```ts
type Profile = {
  kind: "person";
  name: string;
  age: number;
} | {
  kind: "organization";
  name: string;
  officeLocation: string;
};

function describe(profile: Profile): string {
  if (profile.kind === "person") {
    return `${profile.name}さんは${profile.age}歳です`;
  }

  return `${profile.name}の所在地は${profile.officeLocation}です`;
}
```

`profile.kind` の値で場合分けすると、TypeScriptは各分岐で必要なプロパティを自動的に絞り込みます。これを**ナローイング**と呼びます。

この例では、`kind` のようにパターンを判別するためのプロパティを**リテラル型**で定義しています。これを**タグ付きユニオン型**と呼ぶこともあります。処理の結果を表す場合にも有効です。

```ts
type FetchResult =
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function renderResult(result: FetchResult): string {
  if (result.status === "success") {
    return result.data.join(", ");
  }

  return `失敗しました: ${result.message}`;
}
```

`status` を確認した後は、`success` 側では `data`、`error` 側では `message` が使えるとTypeScriptが判断します。booleanだけを使って複数の状態を表現するより、取りうる状態と必要なデータを一緒に定義できるため、実務でも扱いやすい方法です。

## `any` が危険な理由と `unknown` を安全に使う方法

TypeScriptで最も注意したい型の1つが `any` です。`any` は「型チェックをしない」と宣言するようなもので、何でも代入でき、どんなプロパティにもアクセスできてしまいます。

```ts
declare function loadUser(): any;

const user = loadUser();

console.log(user.name);
console.log(user.address.zipCode);
user.save();
```

このコードは、たとえ実行時に `user` が `null` だったり `address` が存在しなかったりしても、TypeScriptは警告しません。その結果、型 safety が失われ、JavaScriptとほぼ同じ状態になります。

`any` が完全に禁止というわけではありません。既存のJavaScriptライブラリとの接続や、型情報が取得できない一時的な処理では必要になる場合があります。ただし、境界を最小限にし、可能であれば正確な型へ置き換えるべきです。

外部から任意の値を受け取る場合は、`any` よりも `unknown` を使うのが安全です。`unknown` は「値が入っていることは分かるが、型が分からない」状態を表します。そのため、型を確認するまではプロパティにアクセスできません。

```ts
const value: unknown = JSON.parse('{"name":"山田太郎"}');

if (
  typeof value === "object" &&
  value !== null &&
  "name" in value &&
  typeof value.name === "string"
) {
  console.log(value.name);
}
```

`typeof` や `in` で確認した範囲だけ、TypeScriptは `value.name` を `string` として扱います。APIレスポンスのように信頼できないデータを扱う場合は、ライブラリを使ったバリデーションと組み合わせ、検証後の値だけをアプリケーション内で使うとさらに安全です。

## 型アサーションは「変換」ではなく「宣言」だと理解する

`as` による型アサーションも、初心者が誤解しやすいポイントです。型アサーションは値を変換しません。「この値はその型だとコンパイラに伝える」だけの処理です。

```ts
const response = await fetch("/api/user");
const data = (await response.json()) as { user: User };

console.log(data.user.name);
```

このコードは、通信失敗、JSON形式の違い、必要なプロパティの欠落などを検出してくれません。`as` を付けた時点で、実行時データの責任が開発者に移ります。

分かっている範囲だけに留めるなら、部分的な型アサーションが役立つ場合があります。

```ts
type UserResponse = {
  user: User;
};

const body: unknown = await response.json();

if (
  typeof body === "object" &&
  body !== null &&
  "user" in body
) {
  const user = (body as { user: User }).user;
}
```

ただし、これも `user` が実データとして正しいことを保証するものではありません。外部APIやフォーム入力など信頼できない値では、`as` で済ませず、事前検証を行う方針がおすすめです。

## 実務でつまずきにくい型定義の書き方

型定義に迷ったときは、次の順序で考えると決めやすくなります。

1. その値はどこから来るかを確認する
2. 取りうる値をすべて列挙する
3. 必須項目と省略可能項目を分ける
4. `null` と `undefined` の意味を区別する
5. 外部境界では検証し、内部では具体的な型を使う

たとえば、検索結果の型は次のように表現できます。

```ts
type SearchState =
  | { status: "idle" }
  | { status: "loading"; query: string }
  | { status: "success"; query: string; items: string[] }
  | { status: "error"; query: string; message: string };

let state: SearchState = { status: "idle" };

function startSearch(query: string): void {
  state = { status: "loading", query };
}

function completeSearch(query: string, items: string[]): void {
  state = { status: "success", query, items };
}
```

状態ごとに必要なデータだけを定義しているため、`loading` なのに `items` へアクセスするようなミスを減らせます。最初に完璧な型を作ろうとするより、「現在発生しうる値」と「発生しない値」を整理することが大切です。

配列や汎用的な処理では、ジェネリクスも有効です。

```ts
function getFirst<T>(items: readonly T[]): T | undefined {
  return items[0];
}

const firstName = getFirst(["山田", "佐藤"]);
const firstCount = getFirst([1, 2, 3]);
```

`T` は、呼び出されたときに具体的な型へ置き換わる型変数です。`string[]` 用の関数と `number[]` 用の関数を別々に作らず、戻り値の型も呼び出し元に合わせられます。

最後に、実務では次の点に注意すると `any` を減らしやすくなります。

- `any` を使った場所をレビュー時に確認する
- 外部データは境界で検証する
- `as` は検証の代替手段にしない
- `unknown` から必要な型へ安全に絞り込む
- 型定義は実際の利用箇所を見て必要に応じて改善する

## まとめ

TypeScriptの型を使いこなすコツは、すべての変数に細かく型を書くことではありません。型の推論を活用しつつ、関数の境界、外部から受け取る値、取りうる状態が複数ある箇所で意図を明確にすることです。

特に重要なのは、次の3点です。

- `undefined`、`null`、ユニオン型の意味を区別する
- `any` は型チェックを避ける手段であり、安易に使わない
- 外部からの値は `as` ではなく検証によって安全な型へ変換する

型はミスを完全に防ぐ魔法ではありませんが、設計中の曖昧さを実装の早い段階で見つける強力な道具です。小さなコードでも「この値は本当に文字列か」「このプロパティは存在するか」と考えながら型定義を改善していくと、実行時エラーを減らし、保守しやすいコードへ近づけられます。
