## git push --force で履歴を吹き飛ばした
**困っていたこと**: feature ブランチでリベース後に `git push --force` を実行し、リモートの履歴を上書きして同僚の作業を消してしまった。  
**正しい使い方**:
```bash
git push --force-with-lease origin feature/branch
```
**変化**: `--force-with-lease` ならリモートが自分以外で更新されていない場合のみ強制プッシュされるため、他人のコミットを守れる。以来、強制プッシュは必ずこのオプションを付けるようになり、事故がゼロになった。

## コミットメッセージを適当に書いて後で追えなくなった
**困っていたこと**: 「fix」や「update」だけのメッセージで履歴を眺めても、何を直したか全く分からず、バグ調査に時間がかかった。  
**正しい使い方**:
```bash
git commit -m "Fix: ユーザー登録時のメール重複チェックを追加 (Issue #123)"
```
**変化**: プレフィックスと課題番号を入れるルールを徹底したら、`git log --oneline --grep="Fix"` で該当コミットが即座に見つかるようになり、調査時間が半分以下に減った。

## docker-compose up -d でボリュームが残ったまま再ビルドしてデータが消えた
**困っていたこと**: `docker-compose up -d --build` を繰り返すうちに、DB のデータボリュームが再作成されてテストデータが毎回消えていた。  
**正しい使い方**:
```yaml
# docker-compose.yml
services:
  db:
    volumes:
      - db_data:/var/lib/postgresql/data
volumes:
  db_data:
```
**変化**: 名前付きボリュームを定義し、`docker-compose down -v` を使わない限りデータが永続化されるようになった。開発サイクルが途切れず、手動でデータ投入する手間がなくなった。

## npm install ではなく npm ci を使わずに CI で依存関係がズレた
**困っていたこと**: ローカルでは `npm install` で動くのに、CI で `package-lock.json` と異なるバージョンが入ってビルドエラーが頻発した。  
**正しい使い方**:
```bash
# CI スクリプト
npm ci
```
**変化**: `npm ci` は `package-lock.json` に完全一致するクリーンインストールを行うため、環境差異が消え、CI 失敗がほぼゼロになった。

## 環境変数を .env ファイルに書き込まずハードコードして本番で漏洩した
**困っていたこと**: API キーをコードに直書きし、リポジトリにプッシュしてしまった。  
**正しい使い方**:
```bash
# .env.example
API_KEY=your_key_here
```
```bash
# 実行時
source .env && node index.js
```
**変化**: `.env.example` だけをコミットし、実環境では `.env` を手動で作る運用に変えたら、秘密情報がリポジトリに入らなくなり、セキュリティレビューもスムーズになった。

## テストを書かずにリファクタリングしてリグレッションを出してしまった
**困っていたこと**: 手動確認だけでリファクタした結果、既存機能が壊れてリリース後にバグ報告が殺到した。  
**正しい使い方**:
```bash
# Jest 例
npm test -- --coverage
```
**変化**: カバレッジ 80% 以上を必須にする CI ルールを追加したら、リファクタ前後に自動で回帰が検知され、リリース後のバグが激減した。

## ログ出力を console.log だけにして本番で原因特定できなかった
**困っていたこと**: エラー時にスタックトレースが出ず、どの関数で落ちたか分からずデバッグに数時間費やした。  
**正しい使い方**:
```js
// logger.js
const winston = require('winston');
const logger = winston.createLogger({
  level: 'info',
  format: winston.format.json(),
  transports: [new winston.transports.Console()]
});
module.exports = logger;
```
**変化**: 構造化ログとレベル分けにより、本番でも `logger.error(err)` でスタックトレースが JSON で出力され、検索・集計が容易になり、障害対応時間が 1/3 に短縮された。

## ブランチ戦略を決めずに main へ直コミットしてリリースが止まった
**困っていたこと**: 全員が `main` に直接 push し、コンフリクトや未完成コードが混入してデプロイが止まることが多かった。  
**正しい使い方**:
```bash
# GitHub Flow 風
git checkout -b feature/issue-456
# 作業後
git push origin feature/issue-456
# PR 作成 → レビュー → マージ
```
**変化**: PR ベースのレビューを必須にしたら、コンフリクトが事前に解消され、リリースフローが安定。デプロイ失敗がゼロになった。

## バックアップなしで DB マイグレーションを実行してデータが壊れた
**困っていたこと**: `rails db:migrate` を本番でいきなり実行し、ロールバック不可のカラム削除でデータ消失。  
**正しい使い方**:
```bash
# 事前バックアップ
pg_dump -U postgres mydb > backup_$(date +%F).sql
# マイグレーション
rails db:migrate
```
**変化**: バックアップスクリプトを CI に組み込み、必ずスナップショットを取ってから適用する運用にしたら、万一のロールバックも数分で完了し、データ損失リスクがほぼ消えた。

## ドキュメントを更新せずに API 仕様が変わってフロントが壊れた
**困っていたこと**: バックエンドだけ仕様変更し、Swagger を更新し忘れたためフロントエンドが 400 エラーを吐き続けた。  
**正しい使い方**:
```yaml
# openapi.yaml の例
paths:
  /users:
    post:
      summary: ユーザー作成
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/UserCreate'
```
**変化**: OpenAPI 定義をコード生成の元にし、CI で `npm run lint:openapi` を通すようにしたら、仕様変更時に自動で検知され、フロントとの齟齬がなくなった。

## まとめ
失敗は誰にでも起こるものですが、それぞれに「次からこうしておけば防げた」という小さな習慣があります。まずは 1 つ試してみてほしい。
