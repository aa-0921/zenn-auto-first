「特定のユーザーの注文履歴をすぐに見せてほしい」「この商品の売上合計を出して」と言われたとき、慌ててテーブル構造を思い出しながら、何度も同じようなSELECT文を書き直していませんでしたか？私も駆け出しの頃は、集計のたびに複雑なJOINを書き間違えたり、条件指定を忘れて膨大なデータを取得してしまい、DBの負荷を上げてしまったりと、SQLの書き方一つで作業が止まってしまうことが多々ありました。

実務では、単にデータを取得するだけでなく、「いかに正確に、かつ効率的に目的の数値に辿り着くか」が求められます。今回は、私がエンジニアとして現場に出てから、データの調査や集計作業で「これを知っておけば本当に助かった」と感じたSQLのパターンを10個厳選して紹介します。

## 特定の条件に一致するデータを探す WHERE 句の活用

以前は、特定のステータスを持つユーザーを探す際、条件を一つずつ追加しては実行し、結果を見てはまた書き直すという作業を繰り返していました。条件が複雑になると、どこで間違えたのか分からなくなることもありました。

SQLでは、`AND` や `OR` を組み合わせることで、複数の条件を一度に指定できます。また、`IN` を使うと、複数の値のいずれかに一致するかをスマートに判定できます。

```sql
-- 特定のステータスを持つユーザーを複数条件で抽出
SELECT * FROM users
WHERE status = 'active'
  AND country IN ('Japan', 'USA', 'UK')
  AND age >= 20;
```

これを使うようになってからは、泥臭く条件を一つずつ試す必要がなくなり、最初から目的のデータセットをピンポイントで取得できるようになりました。調査のスピードが格段に上がりました。

## 重複を排除してユニークな値を確認する DISTINCT

「このアプリには、現在何種類のカテゴリが存在するのか？」といった質問を受けたとき、以前は一度全データを取得してから、Excelやテキストエディタに貼り付けて重複を削除するという、非常に非効率なことをしていました。

`DISTINCT` を使えば、カラム内の重複を取り除いたユニークな値だけを直接取得できます。

```sql
-- 商品テーブルから、存在するカテゴリの一覧を重複なく取得
SELECT DISTINCT category_name FROM products;
```

このコマンドを覚えてからは、DBから直接「正解」を導き出せるようになりました。手元にデータを持ち出す手間が減り、ミスも防げるようになったので、最初から使っておくべき必須の書き方だと感じています。

## データの件数を素早く把握する COUNT 関数

「今、登録されているユーザーは何人ですか？」という単純な問いに対して、以前は `SELECT * FROM users` を実行して、クライアントツールの行数表示を確認していました。しかし、これではデータ量が多い場合に表示が遅れたり、メモリを大量に消費したりするリスクがありました。

`COUNT` 関数を使えば、データの行数だけを高速に集計して返してくれます。

```sql
-- ユーザーの総数を取得
SELECT COUNT(*) FROM users;

-- 特定の条件に一致する件数のみを取得
SELECT COUNT(id) FROM orders WHERE status = 'completed';
```

件数を知るためだけに全レコードを読み込む必要がなくなったため、DBへの負荷を最小限に抑えつつ、一瞬で回答を出せるようになりました。

## データの並び順を制御する ORDER BY

調査中、最新の注文を調べたいときや、売上の高い順に見たいとき、以前は取得したデータをプログラム側やエディタ側でソートしていました。しかし、これではデータの全体像を把握するのが難しく、SQLだけで完結させる方がずっと楽です。

`ORDER BY` を使えば、昇順（ASC）または降順（DESC）で結果を並べ替えて取得できます。

```sql
-- 作成日時が新しい順（降順）にユーザーを表示
SELECT * FROM users
ORDER BY created_at DESC;

-- 価格が安い順（昇順）に商品を表示
SELECT * FROM products
ORDER BY price ASC;
```

「最新のログを見せて」と言われた瞬間に `ORDER BY created_at DESC` を打ち込めるようになると、調査のテンポが崩れず、スムーズに原因究明に移れるようになります。

## データの範囲をスマートに指定する BETWEEN

「先月の売上を集計して」と言われたとき、以前は `date >= '2023-10-01' AND date <= '2023-10-31'` のように、比較演算子を並べて書いていました。間違いではありませんが、記述が長くなると読みづらく、境界値のミス（初日を含めるか、末日を含めるかなど）が起きやすいと感じていました。

`BETWEEN` を使うと、範囲指定を非常に直感的に記述できます。

```sql
-- 2023年10月の注文データを取得
SELECT * FROM orders
WHERE order_date BETWEEN '2023-10-01' AND '2023-10-31';
```

コードがスッキリして読みやすくなるだけでなく、意図が明確になるため、自分自身のレビューやチームメンバーへの共有時にもミスが減り、心理的な負担が軽くなりました。

## テーブル同士を繋いで情報を補完する INNER JOIN

「注文データはあるけれど、その注文をしたユーザーの名前が分からない」という状況に以前はよく陥っていました。別々のテーブルにある情報を手作業で突き合わせるのは、現実的ではありません。

`INNER JOIN` を使えば、共通のキー（IDなど）を介して、複数のテーブルの情報を一つの結果として統合できます。

```sql
-- 注文情報と、その注文を行ったユーザーの名前を紐付けて取得
SELECT orders.id, users.name, orders.total_price
FROM orders
INNER JOIN users ON orders.user_id = users.id;
```

これを使えるようになってからは、リレーショナルデータベースの真価を実感できるようになりました。バラバラのデータが一つにつながる感覚は、エンジニアとして非常に強力な武器になります。

## グループごとに集計を行う GROUP BY

「各カテゴリごとの商品数は？」や「月ごとの売上合計は？」といった、グループ単位の集計が必要な場面は非常に多いです。以前は、全てのデータを取得してからプログラムのループ処理で集計していましたが、これではデータ量が増えると動作が極端に重くなってしまいました。

`GROUP BY` を使うことで、DBエンジン側で効率的にグループ化と集計を行うことができます。

```sql
-- カテゴリごとに商品の個数を集計
SELECT category_id, COUNT(*) as product_count
FROM products
GROUP BY category_id;
```

集計処理をDB側に任せることで、アプリケーション側のメモリ消費を抑え、高速に結果を得られるようになりました。大規模なデータを扱う実務では、避けては通れない重要な技術です。

## 集計結果に対して条件をかける HAVING 句

`GROUP BY` で集計した後、「売上が10万円以上のカテゴリだけを表示したい」といった、集計後の値に対する絞り込みが必要になることがあります。以前は、集計結果を一度プログラムに取り込んでから `if` 文でフィルタリングしていましたが、これは非常に非効率でした。

`WHERE` 句は集計前に条件を絞りますが、`HAVING` 句は集計した後の結果に対して条件を適用します。

```sql
-- 合計注文金額が5000円を超えるユーザーのみを抽出
SELECT user_id, SUM(amount) as total_amount
FROM orders
GROUP BY user_id
HAVING SUM(amount) > 5000;
```

集計とフィルタリングを一つのクエリで完結できるため、コードがシンプルになり、データの抽出ロジックが非常に明確になりました。

## 欠損値や空のデータを扱う IS NULL

「プロフィール画像が設定されていないユーザーを抽出したい」といった、データが入っていない状態（NULL）を扱う場面はよくあります。以前は `WHERE image_url = NULL` と書いてしまい、「結果が一件も返ってこない！」とパニックになったことが何度もあります。

SQLでは、NULLとの比較には `=` ではなく、専用の `IS NULL` または `IS NOT NULL` を使う必要があります。

```sql
-- プロフィール画像が設定されていないユーザーを探す
SELECT * FROM users
WHERE profile_image_url IS NULL;

-- メールアドレスが登録されているユーザーだけを探す
SELECT * FROM users
WHERE email IS NOT NULL;
```

この挙動を理解してからは、データの不備（データクレンジング）の調査がスムーズになりました。NULLの扱いに慣れることは、正確なデータ抽出の第一歩です。

## 部分一致で柔軟に検索する LIKE 演算子

「名前の一部に『田中』が含まれるユーザーを探したい」といった、完全一致ではない検索が必要なとき、以前は検索エンジンを導入すべきか悩んだり、不完全な正規表現を試行錯誤したりしていました。

`LIKE` 演算子とワイルドカード（`%`）を使うことで、文字列の部分一致検索が簡単に実現できます。

```sql
-- 名前が「田中」で始まるユーザーを検索
SELECT * FROM users
WHERE name LIKE '田中%';

-- 名前の中に「田中」が含まれるユーザーを検索
SELECT * FROM users
WHERE name LIKE '%田中%';
```

これを使えば、ユーザー名やメールアドレス、商品名などの曖昧な検索が驚くほど簡単になります。調査の幅が広がり、ユーザーの行動ログを追う際にも非常に重宝しています。

## まとめ

これまで紹介してきた10個のクエリは、どれも基本ですが、実務で毎日、何度も使うものばかりです。これらを使いこなせるようになると、データの調査スピードが上がり、エンジニアとしての信頼性も高まります。

最初は構文を忘れてしまうこともあるかもしれませんが、何度も書いているうちに自然と指が覚えていきます。まずは、今自分が抱えている調査タスクに対して、この中のどれか1つを試してみてください。小さな工夫の積み重ねが、大きな作業効率の向上につながります。
