## Dockerの基礎概念  
### イメージとコンテナの違い  
- **イメージ (Image)**  
  - OS のカーネルやライブラリ、アプリケーションコードなどを読み取り専用で格納したスナップショット  
  - 層（レイヤ）で構成され、レイヤごとに差分だけを保存するため、同じベースイメージを共有して効率的に保存できる  
- **コンテナ (Container)**  
  - イメージを実行時に読み込み、プロセスを起動する実体  
  - コンテナは一時的（`docker run --rm` で終了時に削除）に作られ、同じイメージから何度でも作成可能  
  - コンテナは「実行中のプロセス＋名前空間」なので、イメージと混同しやすいが、実際は動的な実行環境です  

> **ポイント**  
> - イメージは「設計図」、コンテナは「実際に動くもの」です。  
> - 同じイメージから複数のコンテナを同時に走らせても、レイヤは共有されます。

### Dockerfileでイメージを作る  
```dockerfile
# ベースイメージ
FROM node:18-alpine

# 作業ディレクトリを作る
WORKDIR /app

# 依存関係を先にコピーしてキャッシュを活用
COPY package*.json ./

# 依存関係をインストール
RUN npm ci --only=production

# アプリケーションコードをコピー
COPY . .

# コンテナ起動時に実行するコマンド
CMD ["node", "app.js"]
```
- `FROM` でベースイメージを決定  
- `WORKDIR` で作業ディレクトリを設定  
- `COPY` と `RUN` で依存関係をインストール  
- `CMD` で起動時に実行するコマンドを指定  

## docker-compose で複数コンテナを管理  
`docker-compose` は複数のコンテナを一括で管理できるツールです。  
ローカル開発環境では、フロントエンド、バックエンド、データベースなど複数サービスを同時に起動したいケースが多いので便利です。

### docker-compose.yml のサンプル  
```yaml
version: '3.8'

services:
  db:
    image: postgres:15
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  api:
    build: .
    depends_on:
      - db
    environment:
      DATABASE_URL: postgres://dev:dev@db:5432/appdb
    ports:
      - "3000:3000"
    volumes:
      - .:/app
      - /app/node_modules
    command: npm run dev

volumes:
  db-data:
```
- `services` で複数コンテナを定義  
- `depends_on` で起動順序を制御  
- `volumes` で永続化とローカルコードのマウント  
- `volumes` ブロックでデータベースの永続化を設定  

### コマンド例  
```bash
# すべてのサービスをバックグラウンドで起動
docker compose up -d

# ログを確認
docker compose logs -f

# 停止して削除
docker compose down -v
```
- `-d` でデタッチモード（バックグラウンド）  
- `-v` で永続化ボリュームも一緒に削除  

## ローカル開発で Docker を使うメリット  
| 観点 | 伝統的な開発 | Docker を使った開発 |
|------|--------------|---------------------|
| **環境揃え** | OSやライブラリの差異で「動いたはずが動かない」ケースが多い | コンテナ内は同一イメージなので「書いた環境がそのまま再現」 |
| **依存関係** | 依存ライブラリのバージョン管理が煩雑 | `Dockerfile` でバージョンを明示し、イメージに固定 |
| **データベース** | 本番と同じバージョンをローカルにインストールが必要 | 公式イメージを使えば同一バージョンで動作 |
| **チーム共有** | 開発マシンごとに環境設定が必要 | `docker-compose.yml` を共有すれば「もう一度環境構築する必要なし」 |
| **CI/CD** | テスト環境もローカルと同じ設定を作る必要 | Docker イメージをそのまま CI で גייטングしてテスト実行 |

### 具体的な活用例  
1. **フロントエンド開発**  
   - `node:18-alpine` でとにかく軽量。ホットリロードが簡単に実装。  
2. **バックエンド開発**  
   - `python:3.12-alpine` で Flask や FastAPI を動かし、データベースは `sqlite` ではなく `postgres` コンテナを使うことで本番に近い挙動を確認。  
3. **CIジョブ**  
   - GitHub Actions で `docker compose up` してテストを走らせ、`docker compose down` でクリーンアップ。  

>rlige  
> Docker で開発すると「環境差異によるバグ」が減り、デプロイまでのフローがスムーズになります。  

## まとめ  
- **イメージ**は設計図、**コンテナ**は実際に動くもの。  
- `Dockerfile` でイメージを作成し、`docker compose` で複数サービスを一括管理。  
- ローカル開発に Docker を導入すると、環境揃えや依存関係管理が楽になり、チーム全体の生産性が向上します。  

初心者の方は **まずは単一サービス（例えば Node.js アプリ）を Docker で動かす** ところから始め、段階的に `docker-compose` で複数サービスを統合してみてください。  
慣れると「環境構築が自動化された開発フロー」が手に入り、実務でのデプロイやCI/CDにもスムーズに連携できます。
