同じCSSプロパティを何度もタブを開き直して探していた時期があった。スタイルを変更するたびにDevToolsを閉じてソースコードに戻り、再度開き直す。それが当たり前の作業だと思っていた時期が、実は数年前まで続いていた。

## ElementsでCSSをリアルタイム編集して確認する

導入前に困っていたのは、スタイルを微調整するたびにソースコードに戻って上書き保存し、ブラウザをリロードして確認する作業の繰り返しだった。CSSの値を1px変えるだけで5回ほど手順を踏んでいた。

```css
/* 変更前 */
.container {
  padding: 16px;
}

/* Elementsパネルで直接編集して確認 */
.container {
  padding: 24px;
}
```

ElementsパネルのStyles欄で値を直接変更すると、即座にプレビューが反映される。試行錯誤が終わったら右クリックして「Copy → Copy declaration」を選択し、ソースコードに貼り付けるだけで完了する。保存とリロードの手間が完全に消え、スタイル探しが格段に速くなった。

## Consoleで$0を使って選択要素を参照する

DOMを調べるたびに、要素を右クリックして「Inspect」を開き、コンソールに手で要素パスを打っていた。querySelectorで毎回同じセレクタを書くのが面倒で、複雑な階層の要素を参照するのが苦手だった。

```javascript
// 要素を選択した後、Consoleで
$0
// 選択中の要素がそのまま返る
$0.classList.add('highlight');
```

$0はDevToolsで最後に選択したDOM要素を参照する変数だ。Elementsパネルで要素をクリックした直後にConsoleで$0と打つだけで、その要素をそのまま操作できる。イベントリスナーの追加やスタイルの確認が、もはやquerySelectorなしで書けるようになった。

## Networkパネルでリクエストをブロックしてテストする

APIレスポンスが変わらないと悩んでいた。サーバー側を修正するたびにキャッシュの影響もあって、期待通りのデータが返ってくるか确信が持てなかった。オフライン環境でテストしたい時も、本当にオフラインにするのは手間だった。

```text
DevTools → Network → Block request URL
# 例: https://api.example.com/v1/users
```

NetworkパネルのBlockリクエスト機能で、特定のURLをブロックできる。API通信を遮断して、フロントエンドのエラーハンドリングが正しく動くか確認できる。オフラインシミュレーションもNetworkタブのOnlineセレクタで簡単に切り替えられる。テストの幅が広がった。

## Sourcesパネルでブレークポイントを設定してデバッグする

console.logを大量に挟んで動作を確認する時代があった。ログを消すのも忘れがちで、本番環境に含めないように気を遣っていた。ステップ実行したい時も、ログを読んで頭の中で再現していた。

```javascript
// Sourcesパネルで行番号をクリックしてブレークポイント
// F8で再開、F10でステップオーバー
function calculateTotal(items) {
  let sum = 0;
  for (const item of items) {
    sum += item.price; // ここで停止可能
  }
  return sum;
}
```

SourcesパネルでJavaScriptの行番号をクリックするだけでブレークポイントを設定できる。F8で再開、F10で次の行に進む。変数の値をホバーで確認でき、Call Stackも見える。console.logが激減して、デバッグが圧倒的に速くなった。

## Performanceパネルでボトルネックを可視化する

ページが重いと感じていたが、どこが重いのかがわからなかった。ユーザーの操作が遅延する原因を推測でしか絞り込めず、「もしかしたらレンダリングかな」と当て推量だった。

```text
DevTools → Performance → Record → 操作を行う → Stop
```

Performanceパネルで録画を開始し、対象の操作を行った後で停止すると、フレームレートやCPU使用率、レイアウト・ペイントの時間が可視化される。長いタスクがどこで発生しているか、一目でわかるようになる。最適化すべき箇所が明確になり、パフォーマンス改善が実感できるようになった。

## Applicationパネルでローカルストレージを確認する

ローカルストレージに保存したデータが期待通りか確認するのに、毎回ConsoleでlocalStorage.getItemを打っていた。キー名を間違えていたり、JSON.parseを忘れていたりして、原因特定に時間がかかっていた。

```text
DevTools → Application → Storage → Local Storage
# キーと値を直接確認・編集できる
```

ApplicationパネルのStorage欄で、Local StorageやSession Storage、IndexedDBの中身をGUIで確認できる。データを直接編集して動作確認もできる。クッキーの確認もここで可能で、認証周りのデバッグが格段に楽になった。

## Lighthouseでパフォーマンス監査を行う

パフォーマンスの数値が悪いことはわかっていたが、どこを改善すべきか手がつけられなかった。画像の最適化やキャッシュ戦略を自分で調べるのに、毎回同じ記事を読み返していた。

```text
DevTools → Lighthouse → Analyze page load
# カテゴリ: Performance, Accessibility, SEO
```

Lighthouseでページを分析すると、Performance・Accessibility・SEO・Best Practicesのスコアと、改善提案が一覧で出る。具体的な「画像を圧縮してください」「キャッシュヘッダーを設定してください」といった指摘があり、優先順位もついている。監査が5分で終わり、改善効果が可視化できるようになった。

## デバイスモードでレスポンシブデザインを確認する

スマホ表示の確認に、毎回実際の端末を取り出していた。タブレットとスマートフォンの境界線がどこかも、開発マシンだけだとわからなかった。BrowserStackのようなツールは使っていたが、起動が重くて手が止まっていた。

```text
DevTools → Toggle device toolbar (Ctrl+Shift+M)
# デバイス一覧から選択 or カスタムサイズ入力
```

デバイスモードでツールバーを切り替えると、画面サイズをドラッグで自由に変更できる。iPhoneやGalaxyなどのプリセットもあり、ピンチ操作やGPS位置情報のシミュレーションもできる。実機がなくてもレスポンシブの確認が完結するようになった。

## Snippetsでよく使うスクリプトを保存する

Consoleに頻繁に打つスクリプトを、手打ちで毎回入力していた。クッキーのクリアや、特定の要素を強調表示するスクリプトなど、10回に1回使う程度でも毎回書くのが面倒で、結局手動でやっていた。

```javascript
// Sources → Snippets → New Snippet
console.log('Cookie:', document.cookie);
document.querySelectorAll('a').forEach(a => {
  a.style.outline = '2px solid red';
});
```

Snippetsパネルでスクリプトを保存し、Ctrl+Enterで実行できる。よく使うユーティリティやデバッグ用のスクリプトを置いておける。Consoleの履歴に依存しないので、PCを再起動しても残る。作業の補助具として定着した。

## Coverageで未使用のCSS・JSを検出する

バンドルサイズが大きくなっていることはわかっていたが、どのファイルがどれだけ使われていないかがわからなかった。tree-shakingやコード分割を導入したいと思いつつも、現状の把握ができていなかった。

```text
DevTools → Command Menu (Ctrl+Shift+P) → Coverage
# 録画後に使用率がパーセントで表示される
```

Coverageツールで録画を開始し、操作を行うと、各リソースの使用率が表示される。未使用のCSSやJavaScriptが赤い帯で示され、どの行が使われていないかまでわかる。サイズ削減の優先順位が明確になり、本当に必要なコードだけを残す判断材料になった。

## まとめ

最初に紹介したCSSの確認作業から、Coverageでの未使用コード検出まで、DevToolsの機能を知っているか知らないかで作業効率が大きく変わる。まずは1つ試してみてほしい。コンソールで$0を打ってみるだけでも、DOM操作の感覚が変わるはずだ。
