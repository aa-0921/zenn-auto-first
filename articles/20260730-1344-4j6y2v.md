## 前提：今回扱うサンプルスキーマ

解説の共通土台として、以下の3テーブルを想定します。ER図を頭に描きながら読み進めてください。

```sql
-- ユーザーテーブル
CREATE TABLE users (
    id          BIGINT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    email       VARCHAR(255) UNIQUE NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 注文テーブル
CREATE TABLE orders (
    id          BIGINT PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    status      VARCHAR(20) NOT NULL, -- 'pending', 'shipped', 'cancelled'
    total_amount INTEGER NOT NULL,
    ordered_at  TIMESTAMP NOT NULL
);

-- 注文明細テーブル
CREATE TABLE order_items (
    id          BIGINT PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES orders(id),
    product_name VARCHAR(100) NOT NULL,
    quantity    INTEGER NOT NULL,
    unit_price  INTEGER NOT NULL
);
```

**データのイメージ:**
*   `users`: 1万人
*   `orders`: 50万件（ユーザー1人あたり平均50件）
*   `order_items`: 200万件（注文1件あたり平均4アイテム）

インデックスは `orders(user_id)`, `orders(ordered_at)`, `order_items(order_id)` が貼られている前提とします。

## 1. WHERE句の「書き癖」を見直す：サーゲーブリティとインデックス

実務では「動けばいい」ではなく「速く動く」クエリが求められます。WHERE句の書き方一つでインデックスが効くか効かないかが決まります。

### 悪い例：関数でカラムを包むとインデックスが効かない

```sql
-- NG: ordered_at に関数を適用しているため、インデックス範囲スキャンが使えない
SELECT * FROM orders
WHERE DATE(ordered_at) = '2023-10-15';
```

### 良い例：範囲指定でインデックスを活かす

```sql
-- OK: 範囲検索ならB-Treeインデックスが効く
SELECT * FROM orders
WHERE ordered_at >= '2023-10-15 00:00:00'
  AND ordered_at <  '2023-10-16 00:00:00';
```

**ポイント:** カラム側に関数をかけず、値側で調整する癖をつけましょう。`LIKE '%keyword%'` の前方一致以外も同様にフルスキャンの原因になります。全文検索が必要なら `pg_trgm` や Elasticsearch 等の専用ツールを検討してください。

### NULLの扱いに注意する

```sql
-- NG: NOT IN にNULLが含まれると結果が空になる（三値論理の罠）
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders WHERE status = 'cancelled');

-- OK: NOT EXISTS を使うか、NOT IN のサブクエリで NULL を除外する
SELECT * FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id AND o.status = 'cancelled'
);
```

`NOT IN` はサブクエリの結果に `NULL` が1つでも含まれると `UNKNOWN` となり、マッチする行が0件になってしまう有名な落とし穴です。実務では `NOT EXISTS` または `LEFT JOIN ... WHERE right.id IS NULL` パターンを標準とするのが安全です。

## 2. JOINの使い分け：INNER vs LEFT、そして「結合順序」の意識

JOINはデータの「掛け合わせ」ですが、実務では**「どのテーブルを基準（駆動表）にするか」**を意識することがパフォーマンスの鍵になります。

### 基本の使い分け

| JOINタイプ | 用途 | 実務での頻度 |
| :--- | :--- | :--- |
| `INNER JOIN` | 両方に存在するデータのみ欲しい（厳密な紐付け） | ★★★★★ |
| `LEFT JOIN` | 左側（基準）のデータは全件残したい（マスタ参照、集計の土台） | ★★★★★ |
| `RIGHT JOIN` | ほぼ使わない（LEFTで統一可読性を保つ） | ☆☆☆☆☆ |
| `CROSS JOIN` | 組み合わせ全件（マトリクス作成等、特殊用途） | ☆☆☆☆☆ |

### 実務頻出パターン：集計の土台を作る LEFT JOIN

「ユーザーごとの総購入金額」を出すとき、購入履歴がないユーザーも `0円` として残したいケースです。

```sql
SELECT
    u.id,
    u.name,
    COALESCE(SUM(o.total_amount), 0) AS lifetime_value
FROM users u
LEFT JOIN orders o
    ON u.id = o.user_id
    AND o.status <> 'cancelled' -- 結合条件でフィルタリング（WHEREでやるとINNER JOIN化する罠を防止）
GROUP BY u.id, u.name
ORDER BY lifetime_value DESC;
```

**重要:** `LEFT JOIN` したテーブルのカラムで絞り込みをする場合、**`ON` 句に書くか、サブクエリで事前に絞る**のが鉄則です。`WHERE o.status <> 'cancelled'` と書くと、マッチしなかった行（NULL）が弾かれ、実質 `INNER JOIN` と同じ結果になってしまいます。

### パフォーマンス視点：小さいテーブルを駆動表にする

オプティマイザは賢いですが、統計情報が古い場合や複雑なクエリでは意図通り動かないことがあります。

```sql
-- 直近1ヶ月の注文があるユーザーを抽出する場合
-- 悪い例：users(1万件) を全件走査して orders(50万件) と結合しようとする可能性
SELECT u.name FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.ordered_at >= NOW() - INTERVAL '1 month';

-- 良い例：orders 側から絞り込んでから結合する（CTEやサブクエリで明示）
SELECT u.name
FROM (
    SELECT DISTINCT user_id FROM orders
    WHERE ordered_at >= NOW() - INTERVAL '1 month'
) recent_orders
JOIN users u ON u.id = recent_orders.user_id;
```

後者は「直近の注文ユーザーID（数千件）」を先に特定し、小さい結果セットで `users` と結合するため、一般的に高速です。`EXPLAIN ANALYZE` で実行計画を見て、駆動表が意図通りになっているか確認する癖をつけましょう。

## 3. 集計とウィンドウ関数：GROUP BY の壁を越える

`GROUP BY` は便利ですが、「グループ化した結果に元の行の詳細も出したい」という要件には対応できません。ここで **ウィンドウ関数** が威力を発揮します。

### よくある失敗：GROUP BY に含めないカラムを SELECT する

```sql
-- エラーになる（PostgreSQL, MySQL ONLY_FULL_GROUP_BY モード等）
SELECT user_id, product_name, SUM(quantity)
FROM order_items
GROUP BY user_id; -- product_name がグループ化されていない
```

### ウィンドウ関数で「ユーザーごとの累計購入額」を出す

```sql
SELECT
    o.id,
    o.user_id,
    o.total_amount,
    o.ordered_at,
    -- ユーザーごとに、注文日時順で累計を計算
    SUM(o.total_amount) OVER (
        PARTITION BY o.user_id
        ORDER BY o.ordered_at
        ROWS UNBOUNDED PRECEDING
    ) AS cumulative_amount
FROM orders o
WHERE o.status = 'shipped'
ORDER BY o.user_id, o.ordered_at;
```

**ユースケース:**
*   ユーザーの「初回購入日」や「直近3回の平均単価」を出す
*   ランキング（`ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`）
*   前後行との比較（`LAG()`, `LEAD()`）

### 実務定番：最新レコードのみ取得（ROW_NUMBER）

「ユーザーごとの最新の注文1件だけ欲しい」は定番中の定番です。

```sql
WITH ranked_orders AS (
    SELECT
        *,
        ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ordered_at DESC) AS rn
    FROM orders
    WHERE status <> 'cancelled'
)
SELECT id, user_id, total_amount, ordered_at
FROM ranked_orders
WHERE rn = 1;
```

`DISTINCT ON (user_id)` (PostgreSQL固有) や相関サブクエリでも書けますが、ウィンドウ関数の `ROW_NUMBER()` が最も可読性が高く、標準SQLとしてポータブルです。

## 4. サブクエリ vs CTE (WITH句) vs 一時テーブル：可読性と最適化のバランス

複雑なクエリを書く際、どう構造化するかは保守性に直結します。

### CTE (Common Table Expression) をデフォルトで使う

```sql
-- 複雑な集計クエリの良い例
WITH
-- 1. 直近30日の有効注文を抽出（駆動表を小さくする）
recent_orders AS (
    SELECT id, user_id, total_amount
    FROM orders
    WHERE status = 'shipped'
      AND ordered_at >= CURRENT_DATE - INTERVAL '30 days'
),
-- 2. ユーザーごとの集計
user_aggregates AS (
    SELECT
        user_id,
        COUNT(*) AS order_count,
        SUM(total_amount) AS total_spent,
        AVG(total_amount) AS avg_order_value
    FROM recent_orders
    GROUP BY user_id
),
-- 3. 上位ユーザーを特定
top_users AS (
    SELECT user_id
    FROM user_aggregates
    WHERE total_spent > 100000
    ORDER BY total_spent DESC
    LIMIT 100
)
-- 4. 詳細情報を結合して最終出力
SELECT
    u.name,
    u.email,
    ua.order_count,
    ua.total_spent,
    ua.avg_order_value
FROM top_users tu
JOIN user_aggregates ua ON tu.user_id = ua.user_id
JOIN users u ON ua.user_id = u.id;
```

**CTEのメリット:**
1.  **上から下へ読める**（ネストされたサブクエリは内側から読む必要がある）
2.  **デバッグしやすい**（途中のCTEを `SELECT * FROM recent_orders LIMIT 5` 等で確認できる）
3.  **再利用可能**（同一クエリ内で `recent_orders` を複数回参照できる）

### 使い分けの指針

| 手法 | 向いているケース | 注意点 |
| :--- | :--- | :--- |
| **CTE (WITH句)** | **基本はこれ**。可読性、ステップ実行、再利用。 | PostgreSQLでは最適化フェンス（マテリアライズ）になる場合がある（`NOT MATERIALIZED` ヒントで制御可）。巨大中間結果はメモリ/ディスク圧迫のリスク。 |
| **サブクエリ (FROM句/WHERE句)** | 単純なフィルタリング、スカラサブクエリ（1行1列返す）、`EXISTS` 等。 | ネストが深くなると読みにくい。相関サブクエリは行ごとに実行され遅くなりがち。 |
| **一時テーブル / マテビュー** | 中間結果が巨大（数百万行以上）、複数の後続クエリで再利用、インデックスを貼りたい。 | トランザクション管理、権限、クリーンアップの手間が増える。バッチ処理向け。 |

## 5. 実務で「あるある」なアンチパターンとリファクタリング

最後に、コードレビューでよく指摘する・されるパターンをまとめます。

### アンチパターン1: `SELECT *` の常用

```sql
-- NG: カラム追加時にアプリが壊れる、ネットワーク/ディスクI/O無駄、カバリングインデックス効かない
SELECT * FROM orders WHERE user_id = 123;

-- OK: 必要なカラムのみ明示
SELECT id, total_amount, ordered_at FROM orders WHERE user_id = 123;
```

### アンチパターン2: `OR` の乱用によるインデックス無効化

```sql
-- NG: インデックスが使われにくい（ユニオンで書き換え可能なら検討）
SELECT * FROM orders
WHERE user_id = 123 OR product_id = 456; -- product_id は order_items にある想定

-- OK: UNION ALL で分割（重複許容なら UNION ALL、重複除外なら UNION）
SELECT o.* FROM orders o WHERE o.user_id = 123
UNION ALL
SELECT o.* FROM orders o
JOIN order_items oi ON o.id = oi.order_id
WHERE oi.product_id = 456;
```
※ `OR` を `UNION` に書き換えるかは実行計画とデータ分布次第ですが、選択肢として持っておきましょう。

### アンチパターン3: アプリ側でN+1クエリを叩く

SQL単体の話ではありませんが、ORM使用時の定石です。

```python
# NG: N+1問題
users = User.all()
for user in users:
    print(user.orders.count()) # ユーザー数分クエリが飛ぶ

# OK: Eager Loading / JOIN / サブクエリで一発取得
users = User.includes(:orders).all() # Rails例
# またはSQLで事前集計
# SELECT u.*, COALESCE(cnt, 0) FROM users u LEFT JOIN (SELECT user_id, COUNT(*) cnt FROM orders GROUP BY user_id) o ON u.id = o.user_id
```
