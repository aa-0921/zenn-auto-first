## 前提：私のケース

- 前職：法人営業（28歳、社会人6年目）
- 学習期間：8ヶ月（平日2時間、土日は4時間程度）
- 転職先：受託開発、20〜50人規模、Java / Spring Boot 中心
- 現在の役割：業務システムの機能追加、改修、障害調査

書かないこと：年収がいくらになったか、楽だったか、最短ルートは何か。人によって条件が違いすぎるので、参考にならないからです。書くのは「再現性のある進め方」だけです。

## 良かったこと1：曖昧さを分解する力が、そのまま仕様詰めの力になった

営業時代に一番鍛えられたのは、客のふわっとした要望を数字と条件に落とす作業です。これはエンジニアでも同じで、むしろ本質部分です。

たとえば「送料無料にしたい」という要望が来たとき、未経験の頃の私は「フラグを1個足す」ところから始めていました。今は先に条件を洗い出します。

```python
def calc_shipping_fee(cart, user, coupon=None):
    """送料を計算する。仕様の曖昧さを先に潰す。"""
    # 1. 閾値は税込か税抜きか
    FREE_SHIPPING_THRESHOLD = 5000

    # 2. 判定対象は「商品小計」か「割引後」か
    subtotal = sum(item.price * item.quantity for item in cart.items)

    # 3. クーポンは送料無料に影響するか
    if coupon and coupon.free_shipping:
        return 0

    # 4. 離島・沖縄は例外か
    if user.region in ("okinawa", "remote"):
        return 1500

    return 0 if subtotal >= FREE_SHIPPING_THRESHOLD else 500
```

ポイントは、コードを書く前にコメントで論点を4つ並べていることです。これをそのまま要件定義の質問リストにして、レビューや仕様確認の場に出します。「離島は無料対象外で合っていますか？」と聞けるのは、営業で客に条件確認を繰り返してきた経験の賜物でした。20代の同僚が実装スピードで劣っていても、手戻りの少なさで取り返せる場面は想像以上に多いです。

## 良かったこと2：小さくコミットしてレビューを高速に回せた

社会人経験があると、「自分の判断が間違っている前提で人に見せる」のがそれほど怖くありません。これがGitの使い方に出ます。私は最初から、1コミット1論点で切ることを徹底しました。

```bash
# 論点ごとにブラウザで説明できる粒度へ
git switch -c feat/free-shipping-threshold

# 1コミット = 1つの意図。まず仕様の確認だけを先に出す
git add src/shipping.py
git commit -m "feat: 送料無料の閾値判定を追加"

# 離島の例外は別コミットに分ける（レビューの単位を小さく保つ）
git commit -m "fix: 離島・沖縄を送料無料の対象外にする"

git push -u origin feat/free-shipping-threshold
```

レビューで「まず1行目で詰まる」ことが減りました。理由は単純で、差分が小さく、意図がコミットメッセージに書いてあるからです。未経験の頃は「全部まとめて300行」で出して2往復目で差し戻され、そこで心が折れかけていました。小さく出すのは技術ではなく習慣で、これは年齢を重ねた社会人のほうが圧倒的に得意な領域だと思います。

## 良かったこと3：テストで「できた」を自分で確認できるようになった

「動いた気がする」でPRを出さない、これを可能にしたのがテストです。私は実装前に、仕様の曖昧さそのものをテストコードに落としました。

```python
import pytest
from shipping import calc_shipping_fee

def test_4999円は送料がかかる():
    cart = make_cart(total=4999)
    assert calc_shipping_fee(cart, make_user("tokyo")) == 500

def test_5000円で送料無料():
    cart = make_cart(total=5000)
    assert calc_shipping_fee(cart, make_user("tokyo")) == 0

def test_沖縄は金額に関係なく1500円():
    cart = make_cart(total=20000)
    assert calc_shipping_fee(cart, make_user("okinawa")) == 1500
```

境界値の4999/5000を先に書くと、仕様確認のときに「どちらが正しいですか？」と具体的に聞けます。テストは品質のためだけのものではなく、曖昧さを言語化する道具でした。加えて、障害調査でも効いています。再現条件をテストとして書けると、「直った」の根拠を自分で示せるので、周囲からの信頼の貯まり方が違いました。

## 学習の進め方：インプットの比率を3割まで落とした

8ヶ月でやったことを順番だけ書きます。

1. 2ヶ月目まではProgateとドットインストールで全体像だけ掴み、深掘りしない
2. 3ヶ月目から「自分の困りごと」を題材にした小規模アプリを1本作る（私は経費の集計ツール）
3. 4ヶ月目、そのアプリにテストとGitの運用を後付けする
4. 6ヶ月目、READMEと設計メモを整え、コードを人に見せてレビューをもらう
5. 8ヶ月目、応募。ポートフォリオは1本だけ、代わりに説明できる状態にした

効いたのは3と4です。「作り切って、テストがあり、意図を説明できる」状態のアプリ1本は、作りかけが10本あるより強いです。面接で聞かれるのは「何を作ったか」より「なぜそうしたか」なので、判断の理由を言語化できる材料が要ります。

## 現場で感じた手応えとしんどさ

手応えは、障害対応で「まず再現手順をテストで書く」と言えたときと、仕様の矛盾を会議で指摘できたときでした。年下のリーダーに「助かる」と言われたのは素直に嬉しかったです。

しんどさは、技術の前提知識の抜けです。ネットワーク、DBのインデックス、OSの挙動といった「20代のうちに触っておく暗黙知」を、実務と並行して埋める必要がありました。これは今も続いていて、1年経っても解消していません。年齢が有利なのは判断と習慣の部分で、知識の総量は素直に不利です。

## まとめ

20代後半・30代からの転職で良かったことは、非エンジニア経験が「曖昧さを分解する力」に変換され、それが仕様詰め・小さなコミット・テストによる自己確認として実務に直結したことです。逆に、基礎知識の遅れは永続的に補い続ける必要があります。

これから始める人への具体的な提案は3つだけです。1本のアプリを作り切ること、そのアプリにテストを書くこと、コミットを小さく切って人に見せること。年齢は学習の順番と習慣でいくらでも取り返せますが、経験の代わりにはならないので、そこは割り切って地道に埋めていくのが現実的だと思います。
