デプロイ作業を忘れて「本番環境が古いままだった」と気づいたり、テストを回し忘れてバグをマージしてしまったり。個人開発をしていると、こうした「うっかりミス」が本当に怖いです。自分一人だからこそ、つい手動での確認や作業を飛ばしてしまいがちですが、そのたびにプロダクトの品質は削られていきます。

以前の私は、コードをプッシュした後に、自分でターミナルを開いてテストを動かし、ビルドが通るか確認し、さらに手動でサーバーへデプロイコマンドを叩いていました。この「一連のルーチン作業」が、実は開発の大きなストレスになっていたのです。もしこの作業を自動化できたら、どれだけ開発に集中できるだろうか。そう考え始めたのが、GitHub Actionsを使い始めたきっかけでした。

## Lint実行でコードの書き方を統一する

開発を始めたばかりの頃、自分なりの書き方でコードを書いてしまい、後から見返すと「なぜこう書いたのか」と混乱することが多々ありました。また、チーム開発を想定したとき、書き方のルールがバラバラだとレビューの効率も落ちてしまいます。自分一人でも、コードの品質を一定に保つために静的解析を自動化する必要がありました。

そこで導入したのが、ESLintを使ったLintチェックの自動化です。`.github/workflows/lint.yml` というファイルを作成し、プルリクエストが作成されたタイミングで自動的に実行されるように設定しました。

```yaml
name: Lint Check
on:
  pull_request:
    branches: [ main ]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: npm ci
      - name: Run ESLint
        run: npm run lint
```

これを導入してからは、コードの書き方のミスや、使ってはいけない関数を使っているといった初歩的なミスを、マージする前に自動で検知できるようになりました。コードの見た目が整うことで、ロジックの検討に集中できるようになり、開発の心理的ハードルがぐっと下がりました。

## Unit Testの自動実行でバグの混入を防ぐ

「さっき直したはずの機能が、別の場所で壊れていた」という経験は、エンジニアなら誰しも一度はあるはずです。特に、リファクタリングを行った直後は、影響範囲が広いため、手動での全テスト実行は非常に時間がかかり、つい省略してしまいがちでした。テスト漏れは、個人開発において最も避けたい事態の一つです。

そこで、JestなどのテストフレームワークをGitHub Actions上で動かすようにしました。これにより、コードをプッシュするたびに、自動的にすべてのテストが実行される環境を構築しました。

```yaml
name: Run Tests
on:
  push:
    branches: [ main ]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: npm ci
      - name: Run Unit Tests
        run: npm test
```

このワークフローのおかげで、テストが失敗している状態のコードがマージされることが物理的に不可能になりました。バグの早期発見が可能になり、デプロイ後の「あ、壊れた」という絶望感を大幅に減らすことができました。

## Build Checkでビルドエラーを未然に防ぐ

テストが通っても、いざデプロイしようとしてビルドコマンドを叩いたらエラーが出る、という失敗を何度も経験しました。特にTypeScriptを使っている場合、型の不整合によるビルドエラーはよくある問題です。デプロイ作業中にエラーが出るのは、開発のリズムを大きく崩す原因になります。

そこで、テストに加えて「ビルドが正常に完了するか」を確認するステップを追加しました。

```yaml
name: Build Check
on:
  pull_request:
    branches: [ main ]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: npm ci
      - name: Build Project
        run: npm run build
```

ビルドチェックを自動化することで、「コードは書けるけれど、デプロイできない」という最悪の状況を防げるようになりました。マージ前にビルドが成功していることが保証されるため、安心して本番環境へのリリース作業を進められるようになりました。

## Security Scanで脆弱性を早期発見する

個人開発では、外部のライブラリを多用することが多いですが、それらが抱える脆弱性に気づくのは容易ではありません。知らないうちにセキュリティホールを作ってしまっているかもしれないという不安は、常に頭の片隅にあります。セキュリティ対策を後回しにするのは危険だと痛感していました。

そこで、`npm audit` を利用して、依存ライブラリの脆弱性をチェックするワークフローを導入しました。

```yaml
name: Security Scan
on:
  schedule:
    - cron: '0 0 * * *' # 毎日実行
  workflow_dispatch: # 手動実行も可能に
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: npm ci
      - name: Run Security Audit
        run: npm audit
```

これを導入してからは、脆弱性のあるライブラリが混入した際にGitHub上で通知を受け取れるようになりました。セキュリティに対する意識が自然と高まり、より安全なプロダクトを維持できるようになりました。

## Deployment for Preview Environmentsでプレビュー環境を構築

コードを変更した際、ローカル環境で動くのは確認できても、実際のサーバーに近い環境でどう見えるかを確認したくなることがあります。特にフロントエンドの開発では、ブラウザでの見え方が重要です。しかし、毎回手動でサーバーにアップロードして確認するのは非常に手間がかかります。

そこで、プルリクエストごとに一時的な「プレビュー環境」を立ち上げる仕組みを考えました。Firebase HostingやVercelなどのサービスと連携させることで、PRのURLから直接動作確認ができるようにしました。

```yaml
name: Deploy Preview
on:
  pull_request:
    branches: [ main ]
jobs:
  deploy_preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Firebase Hosting
        uses: FirebaseExtended/action-hosting-deploy@v0
        with:
          repoToken: ${{ secrets.GITHUB_TOKEN }}
          projectId: my-project-id
          targetDir: build
```

この仕組みにより、コードをマージする前に「実際の挙動」をブラウザ上で確認できるようになりました。レビューの精度が上がり、手動での確認作業が劇的に削減されました。

## Automatic Deployment for Productionでリリースを自動化

テストもビルドもパスしたなら、あとは本番環境へ反映させるだけです。以前は、SSHでサーバーにログインし、`git pull` をして、ビルドコマンドを叩いて……という作業を毎回手動で行っていました。この作業中に接続が切れたり、コマンドを打ち間違えたりするのが怖くて仕方がありませんでした。

そこで、`main` ブランチへのマージをトリガーとして、本番環境へ自動デプロイするワークフローを作成しました。

```yaml
name: Production Deploy
on:
  push:
    branches: [ main ]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to AWS S3
        run: |
          aws s3 sync./build s3://my-production-bucket --delete
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

デプロイが完全に自動化されたことで、「リリース作業」という特別なイベントが、単なる「マージ作業」へと変わりました。リリースの心理的障壁が下がり、こまめな機能追加が可能になりました。

## Database Migration AutomationでDBスキーマ更新を安全に

アプリケーションのコードを更新する際、データベースのテーブル定義（スキーマ）の変更も伴うことがあります。これを手動で行うと、コードの更新とDBの更新のタイミングがズレてしまい、アプリがエラーを起こす原因になります。DB操作は失敗するとデータの消失につながるため、最も慎重に行うべき作業です。

そこで、デプロイのプロセスの中に、データベースのマイグレーションを実行するステップを組み込みました。

```yaml
name: Database Migration
on:
  push:
    branches: [ main ]
jobs:
  migrate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Migrations
        run: npm run migrate
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

これにより、コードのデプロイと同時にDBの構造も最新の状態に更新されるようになりました。手動でのマイグレーション作業によるミスがゼロになり、データの整合性を保つことが容易になりました。

## Notification for Slack/Discordで開発状況を可視化する

GitHub Actionsが成功したのか、それとも失敗したのか。GitHubの画面を頻繁に見に行くのは面倒ですし、エラーが起きていることに気づくのが遅れることもあります。開発の進捗や異常をリアルタイムで把握したいと感じるようになりました。

そこで、ワークフローの実行結果をSlackやDiscordに通知する設定を追加しました。

```yaml
name: Notify Status
on:
  workflow_run:
    workflows: ["CI/CD"]
    types: [completed]
jobs:
  notify:
    runs-on: ubuntu-latest
    if: ${{ github.event.workflow_run.conclusion == 'failure' }}
    steps:
      - name: Slack Notification
        uses: slackapi/slack-github-action@v6
        with:
          payload: |
            {"text": "Workflow failed: ${{ github.workflow }}"}
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
```

エラーが発生した瞬間にチャットツールへ通知が飛んでくるようになったことで、問題の検知スピードが格段に上がりました。開発に集中していながら、異常事態にもすぐに対応できるようになりました。

## Image Optimizationでパフォーマンスを最適化する

フロントエンドの開発では、画像のファイルサイズがページロード速度に直結します。しかし、高解像度の画像をそのままプロジェクトに含めてしまうことがあり、それがサイトの重さの原因になっていました。画像をアップロードするたびに、手動でリサイズや圧縮を行うのは非常に手間です。

そこで、GitHub Actions上で画像を自動的に圧縮して、最適化されたファイルを生成するワークフローを構築しました。

```yaml
name: Optimize Images
on:
  push:
  branches: [ 'assets/**' ]
jobs:
  optimize:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Optimize Images
        run: |
          npm install imagemin-cli -g
          imagemin assets/images/* --out-dir=assets/optimized
```

このワークフローにより、リポジトリに重い画像を入れても、自動的に軽量化された画像が生成・利用されるようになりました。サイトのパフォーマンスが向上し、ユーザー体験の向上に貢献できました。

## Cleanup Old Artifactsでストレージを節約する

GitHub Actionsでは、ビルド結果やテストのレポートを「Artifacts」として保存できます。しかし、これらを無制限に保存し続けていると、ストレージ容量を圧迫し、管理が煩雑になります。特に個人開発では、不要なファイルが溜まっていくのを防ぎたいと考えました。

そこで、古いアーティファクトを定期的に削除する、あるいは保存期間を限定する設定を行いました。

```yaml
name: Cleanup Artifacts
on:
  schedule:
    - cron: '0 0 * * 0' # 毎週日曜日に実行
jobs:
  cleanup:
    runs-on: ubuntu-latest
    steps:
      - name: Delete Old Artifacts
        uses: actions/delete-artifact@v4
        with:
          name: build-artifacts
          expired
```

（注：実際にはGitHubの標準機能や、特定のライフサイクル設定を利用します）
不要なデータが整理されることで、GitHubのストレージ管理がスムーズになり、開発環境が常にクリーンな状態に保たれるようになりました。

## まとめ

今回紹介した10個のワークフローは、どれも私が実際に個人開発で行ってきたものです。最初は一つひとつを設定するのは大変に感じるかもしれませんが、一度構築してしまえば、それらはあなたの代わりに24時間、休むことなくプロダクトを守り、開発をサポートしてくれます。

「自動化するのは時間がかかるのではないか？」と躊躇するかもしれませんが、その手間は必ず後で大きなリターンとなって返ってきます。まずは、Lintやテストといった、最も身近なものから一つ、試してみてほしいと思います。
