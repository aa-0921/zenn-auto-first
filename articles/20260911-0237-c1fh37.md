同じ作業を何度も手で打っていた。Dockerfile を書き直し、イメージをビルドし、コンテナを起動する作業は毎回同じことの繰り返しで、エラーに悩まされることもあった。手動での作業は時間がかかり、CI の待ち時間も気になっていた。

## キャッシュを活用してイメージ構築を効率化する `docker build -t myapp:v1 .`
**困っていたこと:** 毎回 `docker build` を実行する際、変更の少ない部分も一からビルドされ、時間が掛かっていた。キャッシュが無駄になり、CI での待ち時間も気になっていた。

```bash
docker build -t myapp:v1 .
```

**使ってみてどう変わったか:** このコマンドでベースステージのキャッシュが再利用され、ビルド時間が半分以下に短縮された。CI パイプラインもスムーズに完了するようになり、開発効率が向上した。

## ポートマッピングと名前付きコンテナをワンライナーで `docker run -d -p 8080:80 --name web nginx`
**困っていたこと:** 新しいコンテナを立ち上げる度、`docker run` にポートマッピングやコンテナ名を手入力していた。ミスが発生しやすく、特に本番環境の確認が面倒だった。

```bash
docker run -d -p 8080:80 --name web nginx
```

**使ってみてどう変わったか:** これにより、必要なポートと名前が一度に設定され、コンテナの起動と確認が簡単になった。`docker ps` で即座に状態を確認できるようになり、操作性が大幅に向上した。

## コンテナ内へのシェルアクセスを `docker exec -it mycontainer bash` で実現
**困っていたこと:** 本番環境の問題を調査する際、コンテナ内にログインする方法を忘れたり、`docker attach` と `docker exec` の違いに悩むことがあった。リモートからの操作が手間だった。

```bash
docker exec -it mycontainer bash
```

**使ってみてどう変わったか:** `docker exec -it` を使えば、対話型ターミナルが即座に開き、スクリプトの実行やファイル操作が快適になった。SSH 設定なしで済むのも助かっている。

## コンテナとホスト間のファイル転送を `docker cp` で簡素化 `docker cp mycontainer:/app/src ./local_src`
**困っていたこと:** デバッグやバックアップのため、コンテナ内のファイルをホストにコピーしていたが、手順が煩雑でコピーに失敗することもあった。スクリプト作成も面倒だった。

```bash
docker cp mycontainer:/app/src ./local_src
```

**使ってみてどう変わったか:** このワンライナーで必要なファイルを簡単に抽出できるようになり、手動での scp プロセスが不要になった。開発のスピードが明らかに上がった。

## コンテナのログをリアルタイムで確認 `docker logs -f mycontainer`
**困っていたこと:** エラー発生時に `docker logs mycontainer` を実行し、最新ログだけを見るため再度コマンドを実行していた。最新の状況を逃すこともあり、調査に時間がかかっていた。

```bash
docker logs -f mycontainer
```

**使ってみてどう変わったか:** `-f` フラグでログをフォローできるようになり、即座に問題を特定できるようになった。デバッグ作業が格段に効率的になった。

## 未使用のボリュームをクリーンアップ `docker volume prune -f`
**困っていたこと:** テスト後に残るボリュームを一つずつ削除していたが、`docker volume ls` で確認する手間と削除忘れが課題だった。ディスク容量も徐々に圧迫されていた。

```bash
docker volume prune -f
```

**使ってみてどう変わったか:** `-f` 付きの prune により、未使用ボリュームを一括削除できるようになった。定期的なメンテナンスが数行のコマンドで完了し、ディスクの無駄遣いが減った。

## 不要なネットワークを削除 `docker network prune -f`
**困っていたこと:** 複数のテスト環境で作成したネットワークを個別に削除しており、`docker network ls` で確認する手間と削除ミスが発生していた。環境の整理が困難だった。

```bash
docker network prune -f
```

**使ってみてどう変わったか:** `-f` 付きの prune により、未使用ネットワークを一括削除できるようになった。新しいプロジェクト開始時の環境準備が大幅に短縮された。

## Docker Compose でサービス群を簡単に起動 `docker compose up -d`
**困っていたこと:** 複数のサービスからなるアプリケーションを起動する際、各コンテナを個別に `docker run` していた。設定の重複と起動時間のロスに悩んでいた。

```bash
docker compose up -d
```

**使ってみてどう変わったか:** Compose により `docker compose up -d` 1 つのコマンドで全サービスが起動し、環境構築が数分から数秒に短縮された。開発者の生産性が向上した。

## Compose 環境を停止してクリーンアップ `docker compose down`
**困っていたこと:** 開発が終わると手動で各コンテナを停止し、ネットワークやボリュームを削除していたが、手順が煩雑で忘れがちだった。クリーンな状態を維持するのが困難だった。

```bash
docker compose down
```

**使ってみてどう変わったか:** `docker compose down` により、Compose で定義されたすべてのリソースが一度に停止・削除され、後片付けが簡単になった。次の開発セッションもスムーズに開始できる。

## 全体的なクリーンアップを実行 `docker system prune -a -f`
**困っていたこと:** Docker 上の不要なイメージ、コンテナ、ネットワーク、ボリュームを定期的に手動で削除しており、作業が煩雑でミスが発生していた。ディスク usage の確認も負担だった。

```bash
docker system prune -a -f
```

**使ってみてどう変わったか:** `-a -f` 付きの system prune により、未使用のリソースをまとめて削除できるようになった。ディスクの空き容量を常に確保でき、CI エージェントでの作業も快適になった。

## まとめ
Docker コマンドを効果的に活用することで、日々の開発作業が劇的に効率化された。まずは 1 つ試してみてほしい。小さな変更でも、積み重ねれば大きな成果につながるだろう。
