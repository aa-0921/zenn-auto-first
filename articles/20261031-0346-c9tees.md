開発の現場でAIを使い始めた当初、なんとなく自然言語でリクエストを投げても、希望通りのコードや回答が返ってこず、何度も修正を繰り返していたことがありました。「とりあえず書いて」と言っても、インデントの狂い、不要なコメント、あるいは仕様とズレた実装が返ってきて、時間がかかるだけで終わることも。そんなときにふと試したのが、プロンプトに「型」を持たせることです。指示のクセを整理し、AIに対してより具体的な役割や形式を伝えるようになると、返ってきた成果物の質が劇的に変わりました。同じ悩みを抱えている駆け出しエンジニアの方に、実際に使って効果を実感したプロンプトの型を10個紹介します。

## 役割を明確に定義する型
導入する前に何に困っていたか：目的は伝えても、AIがどの視点からコードを書くべきかわからず、フレームワークやスタイルがブレていた。
具体的な使い方：```Act as a senior frontend engineer specializing in React and TypeScript. Write a reusable component that fetches user data and renders it in a list. Follow the project's existing coding style and use hooks.``` 
使ってみて作業がどう変わったか：役割が明確になると、インデントや型の扱い、ライブラリの選択が一貫し、修正の往復が激減しました。最初から「React engineer」と指定するだけで、意図に沿ったコードが8割方揃います。

## 具体例を Few-shot で与える型
導入する前に何に困っていたか：抽象的なリクエストだけでは、AIが想定する範囲外の実装になり、修正に時間がかかっていた。
具体的な使い方：```# 入力
ユーザーIDから名前を取得する関数

# 期待する出入力
入力: 1 → 出力: "Tanaka"
入力: 2 → 出力: "Sato"``` 
使ってみて作業がどう変わったか：入出力のペアを提示するだけで、AIがパターンを学習し、希望通りの形式で関数を生成してくれました。特に規則正しいデータ変換処理で重宝しています。

## 思考のプロセスを促す型（Chain of Thought）
導入する前に何に困っていたか：単に「作って」と言うと、飛躍したコードが返ってきて、なぜその実装になったのか説明できなかった。
具体的な使い方：```# プロンプト
以下のバグを修正してください。考え方をステップごとに出力し、最後に修正後のコードを提示してください。
[ここにバグのあるコード]``` 
使ってみて作業がどう変わったか：プロセスが可視化されるため、単に動くコードだけでなく、なぜその修正が必要だったのか理解できます。バグ調査の学習機にもなり、自分のコード力も自然と向上しました。

## 条件・制約を明示する型
導入する前に何に困っていたか：無制限に任せると、長すぎるコードや使いたくない機能が含まれ、後で削除する手間があった。
具体的な使い方：```# 条件
- Pythonのみで記述
- 標準ライブラリのみ使用
- 関数の長さは10行以内
- エラー処理は含めない``` 
使ってみて作業がどう変わったか：制約を明示すると、AIが無駄なコードを書かなくなり、スリムで目的達成に特化した実装が返ってきます。レビューの工数も減ります。

## 禁止事項を明示する型
導入する前に何に困っていたか：「やらないこと」を伝え忘れると、AIがつい余分な機能を盛り込んでくれた。
具体的な使い方：```# 禁止
- 画面遷移の実装
- 状態管理ライブラリの使用
- 非同期通信の記述``` 
使ってみて作業がどう変わったか：やってほしくないことをはっきり伝えると、ミニマムな実装に集中できます。プロトタイピングの初期段階で使うと、骨格だけ素早く作れます。

## 文脈・背景情報を注入する型
導入する前に何に困っていたか：ファイルの構造やプロジェクトの規模をAIに共有していなかったため、既存のコードベースに馴染まない実装になった。
具体的な使い方：```# プロジェクト構造
src/
├── components/
│   └── UserCard.jsx
├── hooks/
│   └── useUser.js
# 今回の追加箇所
components/UserList.jsxにユーザーリストを表示する機能を追加してください。``` 
使ってみて作業がどう変わったか：ファイルパスや既存コンポーネント名を共有するだけで、ディレクトリ構造を壊さない範囲での追加実装が可能になります。マージ時の衝突リスクも下がります。

## 出力形式を強制する型
導入する前に何に困っていたか：自然言語の文章で返されると、後で整理やデータベース登録に手間がかかった。
具体的な使い方：```# 指定
以下のフォーマットでJSONを出力してください。
{
  "name": "",
  "age": 0
}``` 
使ってみて作業がどう変わったか：決まった形式で出力させると、次の工程（テストコード作成、DB設計など）への引き継ぎがスムーズになります。スクリプト自動生成の際に特に重宝しています。

## 反復的な改善を促す型
導入する前に何に困っていたか：最初のリクエストで完璧を期しすぎると、時間がかかりすぎて放棄してしまうことがあった。
具体的な使い方：```# プロンプト
まずは最もシンプルな実装を提示してください。その後、順に機能を追加しながら、最終形を目指してください。``` 
使ってみて作業がどう変わったか：小さく始めて徐々に拡張するスタイルに then、AIとの対話が楽しくなり、完成度の高いコードにたどり着きやすくなりました。詰まったときのリセットにも使っています。

## エラー箇所を特定させる型
導入する前に何に困っていたか：エラーメッセージだけをコピペしても、AIが全体を丸ごと書き直してしまい、根本解にならないことがあった。
具体的な使い方：```# エラー
TypeError: Cannot read properties of undefined (reading 'name')
発生場所: UserCard.jsxの35行目
コード: [ここに該当コード]# タスク
このエラーの原因を特定し、最小限の修正コードを提示してください。``` 
使ってみて作業がどう変わったか：エラー箇所と該当コードを添えるだけで、無駄なリファクタリングをせずに原因箇所にピンポイントでアプローチできます。デバッグの時間が半分以下になりました。

## リファクタリングを依頼する型
導入する前に何に困っていたか：既存コードのリファクタリング依頼が vague で、AIが何を変えたかわからない実装になっていた。
具体的な使い方：```# リクエスト
以下のコードをリファクタリングしてください。可読性を上げ、型定義を強化し、テストケースを考慮した形にしてください。
[ここにコード]``` 
使ってみて作業がどう変わったか：リファクタリングの方向性を明示すると、単なる整形にとどまらず、型安全性やテスト可能性が高いコードに生まれ変わります。コードレビューの参考にもなります。

## 比較・選択を促す型
導入する前に何に困っていたか：AかBかの選択に時間がかかり、その都度プロンプトを練っていた。
具体的な使い方：```# プロンプト
次の2つのアプローチのメリット・デメリットを比較し、このプロジェクトの文脈で推奨するのはどちらかを教えてください。
A: REST APIでの実装
B: GraphQLでの実装``` 
使ってみて作業がどう変わったか：比較項目を提示するだけで、プロジェクトの方針に合った選択が瞬時にわかります。新しい技術の導入検討やアーキテクチャ設計の際に重宝しています。

## まとめ
AIに指示する型を意識し始めてから、毎回ゼロからやり取りを始める時間が激減し、希望通りの成果物が返ってくる確率がぐっと上がりました。まずは「役割を明確にする型」から試してみてほしいです。状況に合わせて使い分けるだけで、AIとの対話が開発の一部から強力なアシスタントワークへと変わります。
