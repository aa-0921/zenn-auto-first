## はじめに：AIは「魔法の杖」ではなく「優秀なインターン」だ

Claude Code、GitHub Copilot、Cursor――ここ1年でAIコーディングツールは「便利な補完機能」から「対話型の開発パートナー」へと進化しました。自然言語で指示を出せば、ボイラープレートの生成からリファクタリング、テストコードの作成、さらにはアーキテクチャの提案までこなしてくれます。

しかし、駆け出しエンジニアほど**「つい全部任せてしまい、コードの意味を理解しないままマージしてしまう」**あるいは**「AIが出してきた答えを疑わず、デバッグに時間を溶かす」**という失敗をしがちです。

本記事では、AIツールを「自分でコードを書く力を伸ばすための相棒」として定着させるための、**依存しすぎないバランス**、**聞き方（プロンプト）のコツ**、**人間が書くべき部分と任せる部分の線引き**について、実務目線で整理します。

## 1. 「任せる」と「理解する」の境界線を引く

### 1-1. 「ブラックボックス化」を許さないルールを決める

AIが生成したコードをそのまま本番に入れるのは、見知らぬ他人が書いたコードをレビューなしでマージするのと同じです。以下の**「自分で説明できるか？」**を基準に線引きしましょう。

| 判断基準 | アクション |
| :--- | :--- |
| **ロジックの意図を1行で説明できる** | そのまま採用（レビューはする） |
| **なんとなく動きそうだが、エッジケースが不安** | その場でテストケースを追加させ、動作確認してから採用 |
| **なぜそのライブラリ・設計なのか不明** | 一旦却下し、代替案や理由を聞き直す |

### 1-2. 具体的な運用フロー：PRを出す前に「自分で書き直す」時間を設ける

おすすめなのは、**「AIにドラフトを書かせ → 一旦コピーせず内容を頭に入れ → ファイルを閉じ → 自分でゼロからタイプし直す」**というワークフローです。

```text
【悪い例】
1. 「認証ミドルウェア書いて」と指示
2. 出力されたコードをコピペ
3. 動作確認だけしてPRを出す
→ 後でバグが出ても原因が追えない、修正できない

【良い例】
1. 「JWT検証のミドルウェアをExpressで書いて。エラーハンドリングも含めて」と指示
2. 出力を読み、「verifyトークンの期限切れ・署名不正・欠損の3パターンで401を返す設計だな」と言語化
3. チャットを閉じ、自分で `auth.middleware.ts` を作成して実装
4. 詰まったら再度AIに「このエラーの解消法」だけ聞く
→ 設計意図が頭に入り、デバッグも自分でできる
```

タイプし直す手間は「無駄」ではなく、**「自分の脳にモデルを構築するコスト」**です。このひと手間が、後々の保守性と自身の成長を大きく分けます。

## 2. 「聞き方」で成果が変わる：コンテキスト設計と段階的指示

AIへの指示（プロンプト）は、**「検索クエリ」ではなく「タスクの委任メモ」**として書くのが鉄則です。曖昧な指示は曖昧なコードを生みます。

### 2-1. 必須コンテキストを最初に渡す「システムプロンプト」的運用

プロジェクトごとに、以下の情報を常に冒頭（または `.cursorrules` / `CLAUDE.md` 等の設定ファイル）に含めます。

```markdown
# Project Context for AI
## Tech Stack
- Language: TypeScript (Strict Mode)
- Framework: Next.js 14 (App Router), React 18
- Database: PostgreSQL (Prisma ORM)
- Testing: Vitest + React Testing Library
- Styling: Tailwind CSS

## Conventions
- コンポーネントは関数コンポーネント + Arrow Function で統一
- 状態管理: Server Component優先、Client Componentは最小限
- エラーハンドリング: `neverthrow` の Result 型を使用し、try-catch を極力書かない
- 型定義: `types/` 以下に集約、`any` 禁止、`unknown` から narrow する

## Forbidden Patterns
- `console.log` 本番コードに残さない
- `as Type` の強制キャスト禁止（型ガードで絞る）
- barrel export (`index.ts` からの再エクスポート) 禁止
```

これがあるだけで、「Next.jsで書いて」「Prisma使って」と毎回言う手間が省け、プロジェクト規約に沿ったコードが初回から出やすくなります。

### 2-2. タスクを「設計 → 実装 → 検証」のステップに分解する

一度に「機能作って」と言うと、設計判断をAIに委ねることになります。**設計は人間、実装はAI、検証は人間（＋AI）**という役割分担で指示を出します。

**Step 1: 設計相談（人間が決める）**
> 「ユーザー登録APIを作りたい。メール重複チェック、パスワードハッシュ化(bcrypt)、JWT発行までやる。エラーレスポンス形式は ` { code: string, message: string } ` で統一したい。インターフェース定義だけ先に出して」

**Step 2: 実装指示（AIに書かせる）**
> 「先ほどのインターフェースに基づき、`POST /api/auth/register` のRoute Handlerを書いて。Prismaの `user` モデルは `schema.prisma` 参照。バリデーションはZodで。サービス層 `registerUser` 関数として切り出し、Route Handlerから呼ぶ形にして」

**Step 3: テスト生成とリファクタ（合議）**
> 「この実装に対するVitestの単体テストを書いて。正常系、メール重複、バリデーションエラーの3ケース。あと、`registerUser` 関数の引数を `PrismaClient` ではなく `UserRepository` インターフェースに依存するようDI対応にリファクタして」

このように**「インターフェース先行」「依存関係の方向性指定」「テストファースト」**を指示に含めることで、保守性の高いコードが得られやすくなります。

## 3. 人間が書くべき「核」と、AIに任せる「殻」の使い分け

すべてをAIに任せようとすると、アーキテクチャの整合性が取れなくなります。**「ドメイン知識・アーキテクチャ決定・副作用の境界」**は人間が握ります。

### 3-1. 人間が書く・決めるべき領域（核）

1.  **ドメインモデル・エンティティ定義**
    *   ビジネスルールの核心（例：注文ステートマシン、権限モデル）はAIに丸投げせず、人間が型として定義する。
2.  **アーキテクチャ境界（レイヤー分け・依存ルール）**
    *   `Controller -> UseCase -> Repository` の依存方向、DIコンテナの設定、モジュール分割。
3.  **副作用を伴う境界部分（外部API呼び出し、DBトランザクション制御）**
    *   「ここでロールバックすべきか」「冪等性キーをどう持たせるか」はビジネス判断が必要。
4.  **パフォーマンス要件・セキュリティ要件の実装判断**
    *   N+1問題の解消戦略、レートリミット実装、認可ロジックの配置。

### 3-2. AIに任せて良い領域（殻）

1.  **ボイラープレート・定型コード**
    *   DTO/バリデーションスキーマ（Zod/Yup）、APIクライアントの型生成（OpenAPI Generator等）、マイグレーションファイル雛形。
2.  **テストコードの雛形・網羅パターン生成**
    *   「境界値分析でテストケース列挙して」「モックのセットアップ書いて」
3.  **リファクタリングの機械的作業**
    *   「この関数をアロー関数に」「共通ロジックをカスタムフックに切り出し」「Propsの型を `React.ComponentPropsWithoutRef` で導出」
4.  **ドキュメント・コミットメッセージ・PR説明文の下書き**
    *   「この変更の概要をConventional Commits形式で」「READMEの使い方セクション更新」

### 3-3. 判断に迷ったら「責任を取れるか？」で決める

> **「このコードが原因で本番障害が起きた時、説明責任を果たせるか？」**

AIが書いた正規表現でバリデーションが通ってしまった、AIが選んだライブラリに脆弱性があった――そんな時、「AIがそう書いたから」は通用しません。自分でレビューし、理解し、判断したコードだけを自分のコードベースに取り込む。このスタンスを崩さないことが、AI時代のエンジニアとしての最低ラインです。

## 4. 失敗パターン別・立ち直りのレシピ

駆け出し期によくある「AIとの付き合い方の失敗」と、その修正アクションをまとめました。

| 失敗パターン | 症状 | 即効性のある対処 |
| :--- | :--- | :--- |
| **コピペ依存症** | AIの出力を読まずに適用。エラーが出るとまたAIに聞くループ。 | **「読み上げルール」**：適用前に音読（または心で唱和）し、制御フローをトレースする。 |
| **設計丸投げ** | 「最適な構成で」と言い、後で「なぜこの構造？」となって手戻り。 | **「ADR軽量版」**：決定ログを残す。`docs/adr/001-use-prisma.md` 等に「決定・理由・代替案」を10分で書く。 |
| **デバッグ放棄** | エラースタックトレースを貼るだけで原因特定をAI任せ。 | **「デバッガー強制」**：`console.log` やデバッガーで変数を確認し、「ここまで来てる、ここは来てない」を自分で特定してから質問する。 |
| **最新知識への盲信** | AIが古いバージョンのAPIを出しても気づかず実装。 | **「公式ドキュメント確認ルール」**：主要ライブラリの破壊的変更は必ず公式Changelog/Migration Guideを自分で見る。 |

## まとめ：AIは「タイピング速度」を上げる道具であって「思考速度」を上げる道具ではない

AIコーディングツールを導入して劇的に変わるのは**「手を動かす速度」**です。一方、**「何を作るか」「なぜその設計か」「どう守るか」という思考の速度と質は、依然として人間の経験と訓練に依存します。**

駆け出しエンジニアが今すべきことは、AIを使わないことでも、AIに全部やらせることでもありません。

1.  **「自分で書き直す」儀式**で理解を定着させる
2.  **コンテキストとステップ分解**でAIの出力精度を高める
3.  **責任境界（核と殻）**を意識し、アーキテクチャの主導権を握る

この3点を習慣化できれば、AIは「便利な道具」から「最強のメンター兼実装アシスタント」へと役割を変えます。明日からの開発で、ぜひ「一旦コピペせず、自分でタイプし直す」ところから始めてみてください。
