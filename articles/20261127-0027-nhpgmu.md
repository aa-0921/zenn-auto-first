git diff をコピーしてチャットに貼り、プロジェクト構成の説明を毎回書き直す。そんな使い方を半年続けていました。動いてはいましたが、毎回 5 分は前置きで消えますし、貼り漏れで前提がずれたことも一度や二度ではありません。そこで「毎回手で打っているものを設定に落とす」方針に切り替えました。ツール自体の説明は公式ドキュメントに譲って、自分がどう使って何が変わったかに絞ります。実際に効いた 10 個を紹介します。

```markdown
# CLAUDE.md（プロジェクト直下に置く）
- テスト: `npm test -- --run`
- Lint: `npm run lint`
- スキーマ変更は `npm run db:migrate` のみ。手書き SQL は書かない
```

`/init` で雛形を出してもらってから、効いている行だけ残すのが早いです。会話中に `# ここは必ず型を付ける` と打てば追記できます。初回の説明が不要になり、指示のブレも減りました。

## カスタムスラッシュコマンドで、定型の指示を1単語にする

「この差分にテストを追加して、既存の書き方に合わせて」という指示を毎回長文で打っていました。だいたい同じことを言っているのに、毎回 3 行かかります。

```markdown
---
description: 差分からテストを追加
allowed-tools: Read, Grep, Glob, Edit, Bash(npm test:*)
---
git diff の変更にテストを追加して。既存テストの style に合わせること。
対象: $ARGUMENTS
```

`.claude/commands/add-test.md` として保存するだけで `/add-test` になります。`/add-test 認証フロー` のように引数も渡せます。3 行が 1 単語になり、チームで同じコマンドを使うのでレビュー観点も揃いました。

## サブエージェントに調査を任せて、会話を grep で汚さない

コードベース全体を調べさせると、検索結果が大量に流れて会話が埋まり、肝心の編集で指示が効かなくなることがありました。

```markdown
---
name: explorer
description: 調査担当。設計を相談する前に使う。
tools: Read, Grep, Glob
---
「どこで何が起きているか」を調べ、ファイルパスと行番号付きで報告する。コードは変更しない。
```

`.claude/agents/explorer.md` に保存して、`/agents` から対話的に作ることもできます。調査はここに投げて、メインの会話では要約だけ受け取る形にしました。汚れる量が減って、半日セッションでも指示が通ります。

## settings.json の許可リストで、確認の Enter 連打から解放される

コマンドを1つ打つたびに「実行していいですか?」と聞かれ、ひたすら Enter を押す時間がありました。かといって全許可は怖い。

```json
{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff:*)", "Bash(npm test:*)"],
    "deny": ["Read(./.env)", "Bash(rm -rf:*)"]
  }
}
```

プロジェクト直下の `.claude/settings.json` に置きます。自分だけの内容は settings.local.json に分けて gitignore します。`:*` は「その先の引数は何でも」という指定です。読み取り系だけ許可して `.env` と rm -rf は deny に入れておくと、確認回数が激減して事故も減りました。

## プランモードで先に方針を合意して、手戻りを減らす

「実装して」と頼んだつもりが、下調べなしで 20 ファイル書き換えられ、`git checkout` で戻したことが何度かありました。

```bash
claude --permission-mode plan
```

セッション中は Shift+Tab で default / acceptEdits / plan を切り替えられます。plan は読むだけで編集しないので、方針を文章で出させて合意してから acceptEdits に戻します。ファイルを触られる前に「違う」と言えるようになり、手戻りが減りました。大きめの変更はだいたいこの順で進めるのが自分の中で定着しました。

## ヘッドレスモードで定型レビューをスクリプトに組み込む

PR の diff を毎回目で追うのが辛く、Issue 本文から修正を始めるのも手作業でした。

```bash
# diff を渡して所見をもらう
git diff | claude -p "この差分のリスクを日本語で3点、根拠のファイル付きで"

# ツールとターン数を絞って非対話で実行
claude -p "issue 234 を読んで修正して" --allowedTools "Read" "Edit" "Bash(git diff:*)" --max-turns 20
```

`--output-format json` を付けると結果を jq で扱えます。朝の diff チェックが「読むだけ」になり、CI のジョブにも同じ形で乗せられました。

## フックで lint を自動化して、CI が赤くなる回数を減らす

ファイルを直したあと、自分で lint と型チェックを打つのを忘れて、CI が赤くなってから気づくパターンが多かったです。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command", "command": "npm run lint --silent" }]
      }
    ]
  }
}
```

`.claude/settings.json` に置けばチーム全員で有効になります。毎回走ると重いコマンドは、`matcher` を絞るか PreToolUse 側でチェックだけさせるのがコツです。保存と同時に指摘が出るので、直す場所を忘れずに済みます。

## MCP で仕様書や社内ツールを、コピペなしで参照する

仕様書やチケットの情報を渡すために、ブラウザとエディタを行き来してコピペしていました。DB のスキーマ確認も同じです。

```bash
# ドキュメント用 MCP サーバーを追加(自分用)
claude mcp add --transport stdio docs -- npx -y @modelcontextprotocol/server-filesystem ./docs
claude mcp list
```

セッション中の接続状態は `/mcp` で確認できます。`--scope project` を付けると `.mcp.json` に書かれてチームで共有できます。往復が消えただけでなく、参照先が固定されて回答のブレも減りました。

## /context・/compact・/clear で、後半の精度を落とさない

半日くらい同じセッションで作業すると、関係ないファイルの中身まで残っていて、古い前提で答えられることがありました。何がコンテキストを食っているかも不明でした。

```
/context    # 内訳を確認
/compact 認証まわりの変更に絞って要約して
/clear      # 次のタスクの前に会話をリセット
```

タスクが変わったら `/clear`、同じタスクで長くなったら `/compact` と使い分けています。CLAUDE.md の内容は残るので、説明し直しは不要でした。後半の指示が素直に通るようになりました。

## /rewind と --resume で、やり直しと再開を軽くする

生成された編集が微妙なとき、`git checkout` で戻すと自分の変更まで消えて青ざめました。かといってセッションを閉じると文脈が全部消えます。

```
/rewind   # コードと会話を巻き戻す(どちらを戻すか選べる)
```

エスケキーを2回押しても開けます。戻したあとに同じ指示を出し直すだけで済むので、git の履歴を汚さずに済みます。続きをやりたいときは `claude -c` で直近のセッション、`claude --resume` で一覧から選んで再開します。失敗を恐れずに大きめの変更を任せられるようになりました。

## まとめ

10 個並べましたが、一度に全部入れる必要はありません。まずはプロジェクト直下に CLAUDE.md を1枚置き、次に settings.json で安全なコマンドを許可し、そのあと自分が一番よく打っている指示をスラッシュコマンドにする。この3つだけでも、前置きと確認の回数は体感でかなり減ります。設定は `.claude/` に集まるので、そのままチームに配ると属人性も下がります。使ってみて合わないものは外していけば大丈夫です。まずは1つ、今日試してみてください。
