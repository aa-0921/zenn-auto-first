## ESLintでコード品質を自動チェック
コードレビューで「インデントが崩れている」「未使用変数がある」と指摘されるのが毎回面倒だった。プロジェクトにESLintを導入し、保存時に自動でlintを走らせるようにした。
```bash
npm i -D eslint
npx eslint --init   # 質問に答えて設定ファイルを生成
```
```json
// .eslintrc.json の例
{
  "extends": "eslint:recommended",
  "env": { "node": true, "es2022": true },
  "rules": { "indent": ["error", 2], "no-unused-vars": "warn" }
}
```
これでエディタの保存時にエラーがリアルタイムで表示され、レビューでの指摘が激減した。

## Prettierでフォーマット統一
チーム内でコードスタイルがバラバラになり、差分が見にくかった。Prettierを入れてフォーマットを完全自動化した。
```bash
npm i -D prettier eslint-config-prettier eslint-plugin-prettier
```
```json
// .eslintrc.json に追加
{
  "extends": ["eslint:recommended", "prettier"],
  "plugins": ["prettier"],
  "rules": { "prettier/prettier": "error" }
}
```
```bash
npx prettier --write "src/**/*.js"
```
保存時に自動整形が走り、コードレビューではロジックだけに集中できるようになった。

## HuskyでGitフックを手軽に設定
pre-commitでlintを忘れてしまい、CIで失敗してしまうことが頻繁にあった。Huskyを使うと、簡単にフックを登録できる。
```bash
npm i -D husky
npx husky install
```
```bash
npx husky add .husky/pre-commit "npx lint-staged"
```
これでコミット前にlint-stagedが走り、エラーがあるとコミットがブロックされるため、CIでの失敗がほぼ無くなった。

## lint-stagedでステージングファイルだけlint
全ファイルにlintをかけると時間がかかり、ちょっとした修正でも待たされるのがストレスだった。lint-stagedならステージングされたファイルのみ対象になる。
```bash
npm i -D lint-staged
```
```json
// package.json の一部
{
  "lint-staged": {
    "*.{js,ts}": "eslint --fix"
  }
}
```
コミット対象のファイルだけが高速にチェックされ、開発フローが滑らかになった。

## dotenvで環境変数を管理
ローカル開発時に環境変数を毎回exportしていたら、変数名を typo してしまい、アプリが起動しないことがあった。プロジェクト根底に .env ファイルを置き、dotenvで読み込むようにした。
```bash
npm i dotenv
```
```javascript
// アプリのエントリーポイント例
require('dotenv').config();
console.log(process.env.DB_HOST); // .env に設定した値が取得できる
```
```dotenv
# .env
DB_HOST=localhost
DB_PORT=5432
```
これで環境変数の設定漢字ミスが無くなり、起動時の不安が解消された。

## cross-envでクロスプラットフォームなスクリプト
WindowsとmacOSで環境変数の設定方法が異なり、npmスクリプトが片方だけでしか動かなかった。cross-envを使うと統一的に書けるようになった。
```bash
npm i -D cross-env
```
```json
// package.json の scripts
{
  "scripts": {
    "start": "cross-env NODE_ENV=development node index.js",
    "build": "cross-env NODE_ENV=production webpack"
  }
}
```
どのOSでも同じコマンドで環境変数を設定できるようになり、CI/CDパイプラインも統一できた。

## nodemonで開発中の自動再起動
サーバーコードを変更するたびに手動でCtrl+Cして再起動していたのが面倒で、修正の確認に遅延があった。nodemonを導入して変更を検知したら自動再起動させた。
```bash
npm i -D nodemon
```
```json
// package.json の scripts
{
  "scripts": {
    "dev": "nodemon src/index.js"
  }
}
```
コードを保存するだけでサーバーがリロードされ、フィードバックループが劇的に速くなった。

## concurrentlyで複数プロセスを同時に起動
フロントエンドのビルドとバックエンドサーバーを別タブで起動していて、プロセス管理が煩雑だった。concurrentlyを使うと1つのコマンドで両方を走らせられるようになった。
```bash
npm i -D concurrently
```
```json
// package.json の scripts
{
  "scripts": {
    "dev": "concurrently \"npm run server\" \"npm run client\""
  }
}
```
開発サーバーを一つのタブで起動でき、ログも一つにまとまって見やすくなった。

## chalkでコンソール出力に色付け
デバッグログが白黒で見づらく、重要なメッセージを見逃しがちだった。chalkを使うと簡単に色をつけて視認性を向上させた。
```bash
npm i chalk
```
```javascript
const chalk = require('chalk');
console.log(chalk.green('✅ ビルド成功'));
console.log(chalk.red('❌ エラーが発生しました'));
```
ターミナルに色が付くことで、成功・失敗が一目で分かり、デバッグ効率が上がった。

## zodでランタイムバリデーション
APIのレスポンスが期待通りか不安で、型定義だけでは実行時のミスを防げなかった。zodを使うとスキーマを定義し、データが合っているかをランタイムでチェックできるようになった。
```bash
npm i zod
```
```javascript
const { z } = require('zod');
const UserSchema = z.object({
  id: z.number(),
  name: z.string().min(1),
  email: z.string().email(),
});
// 使用例
const parsed = UserSchema.safeParse(apiResponse);
if (!parsed.success) {
  console.error('不正なレスポンス:', parsed.error);
}
```
不正なデータが混ざると即座にエラーが検出され、本番での予期しない動作が減った。

## まとめ
これらのパッケージはそれぞれ小さな問題を解決するが、組み合わせることで開発フロー全体が格段にスムーズになる。まずは一つだけでも試してみて、日々の作業がどれだけ楽になるか体感してほしい。
