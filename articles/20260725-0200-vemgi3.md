## Dockerとは何か
Dockerは、アプリケーションとその依存関係を一つのイメージにパッケージ化し、どの環境でも同じように動作させるためのプラットフォームです。従仮想マシンと異なり、ホストOSのカーネルを共有する軽量なコンテナ技術を利用するため、起動が速くリソース消費が少ないのが特徴です。これにより、開発者は「俺のマシンでは動く」問題を減らし、CI/CDパイプラインへの組み込みも容易になります。

## イメージとコンテナの違い
イメージは、アプリケーションのコード、ランタイム、ライブラリ、環境変数などを読み取り専用のレイヤーとして積み重ねたテンプレートです。例えば、`FROM node:20` という行は、Node.js 20の公式イメージをベースにすることを意味します。イメージはビルド時に作成され、リポジトリ（Docker Hubなど）にプッシュして共有できます。

一方、コンテナはイメージから起動された実行可能なインスタンスです。コンテナ内ではファイルシステムが書き込み可能なレイヤーが追加され、アプリケーションの実行状態やログが保存されます。コンテナは停止してもイメージは変わらず、同じイメージからもう一度コンテナを起動すれば初期状態に戻せます。この「イメージ＝設計図、コンテナ＝実際の建物」という比喩が理解しやすいでしょう。

## Dockerfileの基本と書き方
Dockerfileは、イメージをビルドするための手順を記述したテキストファイルです。以下はシンプルなNode.jsアプリ用のDockerfile例です。

```dockerfile
# ベースイメージ
FROM node:20-alpine

# 作業ディレクトリを設定
WORKDIR /app

# package.jsonとpackage-lock.jsonを先にコピー（レイヤーキャッシュを活用）
COPY package*.json ./

# 依存関係をインストール
RUN npm ci --only=production

# アプリケーションコードをコピー
COPY . .

# ポートを公開（アプリが3000番でListenしていると仮定）
EXPOSE 3000

# コンテナ起動時のコマンド
CMD ["node", "index.js"]
```

ポイントは、`COPY`と`RUN`の順序です。変更が頻繁にあるソースコードは最後にコピーし、依存関係のインストールは変更が少ない方に置くことで、ビルドキャッシュを最大限に活用できます。また、アルパインサイズの小さなベースイメージを選ぶと、最終的なイメージサイズを大幅に削減できます。

## docker-composeでマルチコンテナ環境を作る
実際の開発では、データベースやキャッシュなど複数のサービスを組み合わせることが多いです。docker-composeを使うと、YAMLファイル一つで複数コンテナの定義とネットワーク設定を管理できます。以下はNode.jsアプリとPostgreSQLを組み合わせた例です。

```yaml
version: "3.9"
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_HOST=db
      - DATABASE_USER=postgres
      - DATABASE_PASSWORD=example
      - DATABASE_NAME=mydb
    depends_on:
      - db
    volumes:
      - ./:/app
      - /app/node_modules  # ボリュームでホストのnode_modulesをマウントしないように

  db:
    image: postgres:15-alpine
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=example
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"

volumes:
  pgdata:
```

`depends_on`で起動順序を指定し、`volumes`でデータの永続化やソースコードのライブリロードを設定しています。`docker compose up -d`コマンド一つで、アプリとDBが同時に起動し、相互に通信できるネットワークが自動で作成されます。

## ローカル開発でのメリットとベストプラクティス
Dockerをローカル開発に導入すると、以下のような利点があります。

1. **環境の統一**  
   開発者全員が同じイメージからコンテナを起動するため、「動く・動かない」の差がほぼなくなります。

2. **依存関係の隔離**  
   ホストにNode.jsやPostgreSQLをインストールする必要がなく、バージョン競合を避けられます。

3. **スナップショットとロールバック**  
   イメージはバージョン管理可能で、問題が起きた際は以前のイメージにすぐに戻せます。

4. **CI/CDへのシームレスな移行**  
   ローカルで使っているdocker-composeファイルは、ほぼそのままGitLab CIやGitHub Actionsで再利用できます。

ベストプラクティスとしては、以下を意識しましょう。

- **マルチステージビルド**を使って、ビルド時の依存関係だけを含む中間イメージを作り、最終イメージには実行に必要なファイルのみを残す。これによりイメージサイズを最小化できる。
- **.dockerignore**を設定し、不要なファイル（log、node_modules、.gitなど）をビルドコンテキストに含めない。
- **ボリュームマウント**でソースコードを共有し、ホスト側でエディタを使いながらコンテナ側で即座に変更を反映させるホットリロード環境を構築する。
- **シークレット管理**はdocker-composeの`secrets`機能や外部のシークレットストア（HashiCorp Vault、AWS Secrets Manager）を利用し、平文のパスワードをYAMLに書かない。

## まとめ
この記事では、Dockerの基本概念であるイメージとコンテナの違いを整理し、Dockerfileの書き方とdocker-composeによるマルチコンテナ環境の構築方法を具体的に示しました。さらに、ローカル開発におけるメリットと実践的なベストプラクティスを紹介しました。これらの知識を踏まえて、`docker build`と`docker compose up`を日常のワークフローに組み込めば、環境依存のバグを減らし、開発スピードを向上させることができます。ぜひ手元のプロジェクトにDockerを導入し、快適な開発体験を手に入れてください。
