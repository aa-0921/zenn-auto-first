## 背景・前提
- **プロジェクト構成**：Next.js のプロジェクトは `next create next-app` で生成され、デフォルトでは `pages` ディレクトリにページコンポーネントが配置されます。App Router を利用する場合は `app` ディレクトリを作成し、そこにルーティングやレイアウトを定義します。
- **バージョン**：ここでは Next.js 13.4 以降を前提に解説します。 older 版では Pages Router が唯一の選択肢でした。
- **コンポーネントの種類**：Next.js では「サーバーコンポーネント」と「クライアントコンポーネント」の二種類が存在します。サーバーコンポーネントはデフォルトでサーバー側で実行され、クライアント側でのみ動作するコンポーネントは `use client` ディレクティブを追加します。

## App Router と Pages Router の違い
### 1. ディレクトリ構造
- **Pages Router**（従来）  
  ```
  /pages
    index.js          // / のハンドラ
    about.js          // /about のハンドラ
  ```
  各ファイルがルーティングを決定します。動的ルーティングは `[id].js` のようにファイル名で実装します。

- **App Router**（Next.js 13+）  
  ```
  /app
    layout.js         // アプリ全体のレイアウト（すべてのページに適用）
    page.js           // app/ のトップページ
    about/page.js     // /about ページ（子ページ）
    about/layout.js   // /about に対する独自レイアウト
  ```
  `app` ディレクトリは「セグメント」ごとにフォルダを作り、各フォルダに `page.js`（ページ）と `layout.js`（レイアウト）を配置します。これにより、**ネストされたルーティング**と**共有レイアウト**が自然に実装できます。

### 2. データ取得の方法
- **Pages Router**  
  ```jsx
  // pages/posts/[id].js
  import { useRouter } from 'next/router';
  import fetch from 'isomorphic-unfetch';

  export async function getStaticPaths() {
    const res = await fetch('http://localhost:3000/api/posts');
    const posts = await res.json();
    return {
      paths: posts.map(p => ({ params: { id: p.id.toString() } })),
      fallback: false,
    };
  }

  export async function getStaticProps({ params }) {
    const res = await fetch(`http://localhost:3000/api/posts/${params.id}`);
    const post = await res.json();
    return { props: { post } };
  }

  export default function Post({ post }) {
    return <div>{post.title}</div>;
  }
  ```
  データ取得は `getStaticProps` や `getServerSideProps`、またはクライアントサイドでの `fetch` が主流です。

- **App Router**  
  ```jsx
  // app/posts/[id]/page.jsx
  import { notFound } from 'next/navigation';
  import { Metadata } from 'next';

  export async function generateStaticParams() {
    const res = await fetch('http://localhost:3000/api/posts');
    const posts = await res.json();
    return posts.map(p => ({ params: { id: p.id.toString() } }));
  }

  export async function generateMetadata({ params }: { params: { id: string } }): Promise<Metadata> {
    const res = await fetch(`http://localhost:3000/api/posts/${params.id}`);
    const post = await res.json();
    return {
      title: post.title,
      description: post.excerpt,
    };
  }

  export default async function Page({ params }) {
    const res = await fetch(`http://localhost:3000/api/posts/${params.id}`);
    const post = await res.json();
    if (!post) notFound();
    return <article>{post.title}</article>;
  }
  ```
  `generateStaticParams` と `generateMetadata` がページごとに呼ばれ、**ビルド時に静的プリレンダリング**や **SSR** を自動的に選択できます。これにより、データ取得ロジックがページ単位で分離しやすくなります。

### 3. レイアウトの共有
- **Pages Router**  
  レイアウトは `_app.js` でグローバルに定義し、ページごとに上書きする形になります。ネストされたレイアウトは手動でコンポーネントを渡す必要があります。

- **App Router**  
  `layout.js` を各ディレクトリに配置するだけで、**自動的に子ページに共通の UI を提供**できます。たとえば `app/dashboard/layout.js` を作ると、 `/dashboard/*` の全ページで同じヘッダー・フッターが適用されます。

## サーバーコンポーネントとクライアントコンポーネント
### 1. サーバーコンポーネントの特徴
- **デフォルトでサーバー側で実行**され、クライアントへのダウンロードを最小限に抑えます。
- データ取得（例: `fetch`）やサーバー側のロジックをそのまま記述可能です。
- **注意点**：`use client` がない限り、イベントハンドラや状態管理（`useState`, `useEffect`）は使えません。

```tsx
// app/components/ServerHeader.jsx
export default function ServerHeader() {
  // サーバー側で実行されるため、fetch が可能
  const data = await fetch('http://localhost:3000/api/hello').then(r => r.json());

  return (
    <header>
      <h1>{data.message}</h1>
    </header>
  );
}
```

### 2. クライアントコンポーネントの使い方
- **`use client` ディレクティブ**をファイルの最上部に追加すると、そのコンポーネントはクライアントサイドでのみ動作します。
- 状態や副作用を持つコンポーネント（例: ボタンのクリック処理）に必須です。

```tsx
// app/components/ClientButton.jsx
'use client';

import { useState } from 'react';

export default function ClientButton() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      Clicked {count} times
    </button>
  );
}
```

### 3. 混在させた例
```tsx
// app/page.jsx
import ServerHeader from '@/components/ServerHeader';
import ClientButton from '@/components/ClientButton';

export default function Page() {
  return (
    <main>
      <ServerHeader />
      <ClientButton />
    </main>
  );
}
```
上記のように **サーバーコンポーネントとクライアントコンポーネントを組み合わせ** すれば、データ取得はサーバーで行い、インタラクティブな要素はクライアントで処理でき、パフォーマンスとUX の両面で最適化できます。

## まとめ
- **App Router** はファイル系統ベースのルーティングとネストレイアウトが強みで、Pages Router に比べて開発効率が向上します。  
- **Pages Router** はまだまだ残っているため、既存プロジェクトの維持やシンプルな構造では併用が可能です。  
- **サーバーコンポーネント** はデータ取得やサーバー側ロジックを書くのに最適で、ページのロード速度を大幅に改善します。  
- **クライアントコンポーネント** は `use client` を明示的に追加し、インタラクティブな要素を実装します。  
- 初心者が最初に躓きがちなのは **「どのディレクトリで何を書くか」** と **「コンポーネントの実行環境」** を混同する点です。上記の構造とコード例を参考に、まずは小さめのサンプルアプリを作りながら概念を確認してみてください。

実務でのチェックリストとしては次の通りです。
1. `app` ディレクトリを作成し、`layout.js` と `page.js` をベースにルーティングを設計する。  
2. データ取得は `generateStaticParams` / `generateMetadata` でサーバー側に書くか、クライアント側で `fetch` するかを選択。  
3. 静的ページか動的ページかを判定し、`generateStaticParams` を使うとビルド時間を短縮できる。  
4. インタラクティブ要素は必ず `use client` が付いたコンポーネントで実装する。

これらを意識すれば、Next.js の「入門」から「つまずき」までスムーズに進められるはずです。ぜひ、実際にコードを書いてみて、違いを体感してください。
