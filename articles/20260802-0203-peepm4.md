## Dockerとは何か？イメージとコンテナの違い

Docker は「コンテナ型仮想化」技術のことです。理解のために、まず「イメージ（Image）」と「コンテナ（Container）」の違いを確認しましょう。

### イメージ（Image）とは

イメージは、コンテナを作成するための「雛形」や「テンプレート」のようなものです。OS のファイルシステム、インストール済みのソフトウェア、設定情報などがすべて詰まっています。

例えば、`nginx:alpine` イメージは、軽量な Alpine Linux 上に Nginx がインストールされた状態です。このイメージを元にして、複数のコンテナを起動できます。

イメージは Dockerfile で定義されます。

```dockerfile
FROM nginx:alpine
COPY ./html /usr/share/nginx/html
EXPOSE 80
```

### コンテナ（Container）とは

コンテナは、イメージを元にして実際に動かした「実行中の環境」です。イメージは不変で一度作成すれば何度でも使えるのに対し、コンテナは起動・停止・削除を繰り返すものです。

```bash
# イメージを元にコンテナを起動
docker run -d -p 8080:80 --name my-nginx nginx:alpine
```

イメージとコンテナの関係は、「設計図」と「出来上がった製品」の関係に似ています。設計図（イメージ）を元に、必要なだけ製品（コンテナ）を作ることができます。

## docker-compose の基本

単一のサービスだけでなく、複数のサービス（DB、Redis、キューなど）をまとめて管理したい場面は多いです。そんなときに便利なのが `docker-compose` です。

### docker-compose.yml の書き方

プロジェクトディレクトリに `docker-compose.yml` を作成し、サービス構成を記述します。

```yaml
version: '3.8'

services:
  web:
    build: .
    ports:
      - "8080:80"
    volumes:
      - ./src:/var/www/html
    depends_on:
      - db

  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: password
      MYSQL_DATABASE: myapp
    volumes:
      - db_data:/var/lib/mysql

volumes:
  db_data:
```

この構成では、`web` サービスと `db` サービスをまとめて管理しています。`depends_on` により、DB が起動してから Web が動くようになっています。

### よく使うコマンド

```bash
# コンテナを起動（バックグラウンドで）
docker-compose up -d

# コンテナを停止
docker-compose down

# ログを確認
docker-compose logs -f

# 再構築してから起動
docker-compose up --build -d
```

## ローカル開発で Docker を使うメリット

### 1. 環境の一貫性

「開発マシン」と「本番環境」が同じ構成になるため、動かない問題が激減します。イメージが変われば環境も変わるので、チーム全員が同じ環境を共有できます。

### 2. 依存関係の管理が楽

Node.js のバージョンも Python のバージョンも、好きなだけ試すことができます。`node:14` イメージで試して、`node:18` イメージで試す、といった切り替えがワンコマンドで完了します。

### 3. データベースのセットアップが簡単

ローカルで MySQL や PostgreSQL をインストールしたくない場合、Docker コンテナだけで完結します。永続化したいデータは `volumes` にマウントすれば、コンテナを削除してもデータは残ります。

## 実践：簡単な Web 開発環境を作ってみる

### ディレクトリ構成

```
my-app/
├─ docker-compose.yml
├─ src/
│  └─ index.html
└─ Dockerfile
```

### Dockerfile の作成

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install -g serve
COPY ./src /app
EXPOSE 3000
CMD ["serve", "-s", "/app"]
```

### docker-compose.yml の作成

```yaml
version: '3.8'

services:
  app:
    build: .
    ports:
      - "3000:3000"
    volumes:
      - ./src:/app
```

### 起動手順

```bash
# ターミナルでプロジェクトディレクトリに移動
cd my-app

# ビルドして起動
docker-compose up --build -d

# ブラウザで確認
# http://localhost:3000
```

`volumes` の設定により、`src` ディレクトリの内容はホストとコンテナで共有されます。そのため、ファイルを編集するとコンテナを再起動せずに反映されます。

## トラブルシューティング

### ポートが競合する場合

```bash
# 既に占有されているポートを確認
lsof -i :8080

# 他のポートに変更
ports:
  - "8081:80"
```

### コンテナが起動しない場合

```bash
# ログを確認
docker-compose logs -f

# 停止中のコンテナを確認
docker-compose ps

# 一度全てをDownしてから再起動
docker-compose down && docker-compose up -d
```

## まとめ

Docker は「環境の不一致」という最大の脅威を奪い去ってくれます。イメージとコンテナの関係を正しく理解し、`docker-compose` で複数サービスを管理すれば、ローカル開発の生産性が劇的に向上します。

まずは単一のサービスから始めて、徐々にデータベースやキューを追加していくことをおすすめします。実践を重ねることで、Docker が「ツール」ではなく「開発の基盤」になるでしょう。
